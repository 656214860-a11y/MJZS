## Standards

### S1 [P1] 排队请求在切项目后可能跨项目执行

- 位置：desktop.py:1767–1769；safe:1993、load:3643、switch:3818。
- 触发：模型槽位不足，项目 A 的请求排队；等待时从侧栏切到项目 B，再获得槽位。
- 依据：排队尚未调用 async_，worker 未置忙，safe 仅检查 worker；load 改写 self.root，没有取消这个请求。dispatch 的 ask 到真正执行时才读取 self.root，却携带 A 的 submission/value。
- 影响：可能使用 B 的配置处理 A 的素材并把输出写入 B，破坏项目上下文隔离；项目 B 若前置条件不足，也可能收到与本次输入无关的阶段错误。
- 建议：提交时冻结项目、模型配置和请求归属；切换项目显式取消旧排队请求；投递与结果消费均校验所属项目，不能只依赖全局 worker。

### S2 [P1] 中断排队只停止轮询，遗留票据阻塞其他排队请求

- 位置：desktop.py:1784–1785、1911–1939；workflow_process_registry.py:57–62。
- 触发：纯 API 模式槽位满，请求排队后点击中断；其他请求也已经进入队列。
- 依据：poll_slot 因 requesting 为假或取消事件而直接退出；interrupt 没有撤销 request['ticket']。注册表仅允许最早可运行票据领取槽位，该无人领取的票据仍在队首。无本地子进程时 poll_flow_processes 直接返回，也不会代为撤销。
- 影响：即使容量恢复，后续已经排队的请求仍持续等待。并非所有新请求必然阻塞，因为新申请可能直接拿到空槽位。
- 建议：让请求生命周期持有票据，在取消、退出、切项目及异常路径撤销该票据并释放已获槽位；按请求取消，避免误撤同项目其他任务。

### S3 [P2] 刷新恢复正文的重试不支持实际取消

- 位置：desktop.py:1888、1907。
- 触发：历史内部回复修复返回 retry_creative，点击刷新启动重新生成，再点击中断。
- 依据：恢复路径 begin_request(cancellable=False)，调用 reply_to_writing 不传 cancelled；正常发送路径则传 cancelled.is_set。
- 影响：UI 丢弃回调后后台仍可能继续四角色和保存，与界面“不再进入后续角色或落盘”提示不符，并可能与下一次请求重叠。
- 建议：恢复请求复用正常发送的取消、槽位和项目快照机制，避免第二套不完整请求生命周期。

## Spec

### F1 [P2] 下载混合模型历史，可能下载旧稿并标错模型来源

- 位置：desktop.py:1947、1952–1957；idea_chat.py:226–245、1131–1136。
- 触发：A 已产出完整剧本，切换到还没有回复的 B 后下载；或多模型都有历史且目录遍历末尾不是最新输出模型。
- 依据：聊天按当前模型过滤，下载按钮及下载正文却调用不接受 model 的 latest_text。其 load 汇总全部模型历史，拼接顺序没有按时间排序；保存时又取当前模型身份。
- 影响：用户得到与当前气泡不同的稿件，并将 A 的正文归档为 B 来源；“最新”也未必是按时间最新。
- 建议：按钮判定和下载使用当前模型会话的同一条完整回复，保存来源取该消息记录；不要用当前配置给跨模型检索结果补来源。

### F2 [P2] 允许上传五份附件，发送却静默只取三份

- 位置：idea_attachments.py:18、294–309；idea_chat_controller.py:30–31；stage_execution_service.py:335–338。
- 触发：一次上传四或五份有效且总字数未超预算的附件，随后正常发送，或显式引用超过三份。
- 依据：上传及 prepare 的 MAX_FILES=5，预检可以成功并在 UI 显示全部入库；发送时 referenced 最后无条件 unique[:3]。最近三份的历史回退限制也错误作用于用户本次明确选择。
- 影响：后两份选中素材不进入模型上下文，也不进入 brief_sources 提取，发送前没有数量截断错误提示；返回引用名单虽可发现差异，但请求已经漏素材。
- 建议：显式选择按 MAX_FILES 验证并完整提交，只对未显式选择的历史回退限制三份；超限明确拒绝，不静默截断。

本轴共 2 项 P2；最高影响为下载错稿及来源错误。
