## 一、复现（精确匹配用户日志）

用诊断时读取的用户项目配置（具体项目名称与路径已脱敏；`script.model = deepseek-v4.1-flash-1017`，6 个 SKILL）跑 `workflow_settings.freeze_skills()`：

```
RAISED: SKILL请求上下文超过 300,000 字符（当前 334,580），请缩短输入、拆分任务或先生成摘要后重试。
主要占用：阶段文档/任务说明 413,105 token。可选择：阶段文档/任务说明可缩短或拆到下一阶段。
```

与 `程序/logs/app.log:1975`（2026-11-18 02:18:51）**逐字一致**，`334,580` 非近似。

逐 SKILL 内联体量累加 = 333,554 字符，加 `<skill>` 包裹后正是 334,580。同一报错在 `app.log` 出现 **6 次**（L1916/1917/1934/1950/1972/1975），跨 11-17 14:19 至 11-18 02:18，是稳定复现。

## 二、根因：四层缺陷叠加

| # | 缺陷 | 位置 | 实测证据 |
|---|---|---|---|
| **D1** | 模型记录为空 `context_length` 时 `_skill_inline_budget()` 返回 `None`＝不设限 | `orchestrator/skill_inline.py:24-35` | `deepseek-v4.1-flash-1017` → `context_length=''` → `budget=None` |
| **D2** | 预算只对**引用**计费；SKILL 顶层正文从不计费 | `orchestrator/workflow_settings.py:696-734`、`skill_inline.py:38-46` | `short-drama-director` 正文 78,991 token，`charged=0` 仍放行 |
| **D3** | 窗口拿不到时 `skill_inline_token_budget(0)` 返回 `None`（不设限），与 D1 叠成**双重静默失效** | `contract/workflow_context_budget.py:37-48` | `skill_inline_token_budget(0) = None` |
| **D4** | 报错把整份 SKILL 正文标成「阶段文档/任务说明」 | `workflow_settings.py:781-782` 未传 `sections` → 回退 `{'stage': prompt}`（`workflow_context_budget.py:201-203`） | 413,105 token 实为 SKILL 正文，标签错误 |

**为什么上一轮「修了没生效」**：R1434／R1435 只把上限从 96,000 抬到 300,000，是**调阈值**不是修机制。D1/D2 未动，`short-drama-director` 全包约 989K 后必然再越线。不是回归，是从未修在预算机制上。

## 三、更深一层：字符硬闸与 token 窗口根本性错配

由用户真实报错反推：334,580 字符 = 413,105 token ⇒ **每字符约 1.235 token**（中文为主）。

300,000 字符硬闸 ≈ **370,409 token**。对照各窗口：

| 模型窗口 | 硬闸允许的 token 是窗口的几倍 | 引用预算 |
|---|---|---|
| 32,000 | **11.6 倍** | 21,184 |
| 64,000 | **5.8 倍** | 46,464 |
| 128,000 | **2.9 倍** | 93,440 |
| 200,000 | **1.9 倍** | 146,000 |
| 1,000,000 | 0.4 倍 | 730,000 |

**字符硬闸只在 1M 级窗口才起保护作用；32K–200K 的真实窗口下它允许的请求远超模型可吃量。** 本该由 D3 的 token 判断兜底，但 D1/D3 双双返回 `None`，只剩这道错配的字符闸。

## 四、修复方案（已用原型验证，待开修复轮落地）

### 4.1 用户已裁定

| 决策 | 裁定 |
|---|---|

| `deepseek-v4.1-flash-1017` 真实窗口 | **128,000** |

### 4.2 必须先纠正的事实：provider 预设表不存在

用户原前提「模型管理都有预设默认值（按 provider 标准预设）」与代码不符，已逐项查证：

- `PROVIDERS`（`infra/model_pool.py:67`）只有 3 个**展示标签**，源码注释明写「它只是标签」。
- `FIELDS`（`:31`）15 个字段**不含** `context_length` 默认值。
- `PROVIDER_WIRES`（`:75`）只映射协议，不映射窗口。
- 唯一预设是 4 条 `BUILTIN` 的**逐模型**硬编码（`:98/104/109/115`）。
- 全库 `DEFAULT_CONTEXT`／`CONTEXT_PRESET`／`WINDOW_PRESET` 零命中。

现状空窗口分布（用户模型池实测）：

```
deepseek-v4.1-flash-1017  ctx=''       ← 本次故障所用
gemini-3.5-flash          ctx=''
gemini-3.8-flash-high     ctx=''
Claude Code / codex / claude  ctx=''
deepseek-v4.1-flash-free  ctx=200000   ← 同族却有值
```

⇒ 预设表需**新建**。因同族一条有值一条无值，且多条 provider 同为「OpenAI 兼容」区分不出厂商，**按模型 ID 前缀分档**（用户已同意）比按 provider 更贴实际。

### 4.3 ⚠ 关键发现：单阶段修法已被证伪，必须两阶段

原型实测三版，前两版**都被证伪**，其失败本身确定了正确修法：

**证伪 1 —— 只补窗口（仅修 D1）**：128K／200K 都能「发出去」，但估算 token 达 150,945／207,563，**仍在窗口外**：

```
window=128000  可发送  est=150945  落在窗口内=False
window=200000  可发送  est=207563  落在窗口内=False
```

⇒ 只修 D1 只是把「被字符闸拦住」变成「发给模型后必定报错」。**不能只修 D1。**

**证伪 2 —— 正文先扣（直觉版 D2）**：`freeze_skills` 里 6 个 SKILL **共享同一个 budget 字典**。第一个技能（`pipeline-script-preparation`）的**引用**几乎吃光预算，剩 306／402／125／379 token，后续 5 个技能正文一分钱都分不到：

```
失败: SKILL 自身正文 16280 token 超出剩余预算 306（README_ZH.md）
```

⇒ 「正文先扣」不能解决，因为预算在技能之间被引用先行消耗。**必须两阶段。**

**正确修法 —— 两阶段预算**（原型实测通过）：

- **阶段一**：先为全部所选 SKILL 的**正文**预留预算（正文不可省，硬需求）。
- **阶段二**：剩余预算才分给引用，按顺序内联，装不下记 `skipped`。

实测结果：

| 窗口 | 引用预算 | 正文需求 | 留给引用 | 结果 |
|---|---|---|---|---|
| 32,000 | 21,184 | 58,414 | −37,230 | 正文放不下 |
| 64,000 | 46,464 | 58,414 | −11,950 | 正文放不下 |
| **128,000** | **93,440** | **58,414** | **+35,026** | **可发送** chars=94,479 est=96,363 内联3 跳过10 **落在窗口内=True** |
| 200,000 | 146,000 | 58,414 | +87,586 | 可发送 est=148,958 在窗口内=True |

**128,000 可行已实证**（用户选定值恰好是最低可用档）。
