# 专题五「任务与自动流程」盘点报告

轮次：R3993 ｜ 类型：只读诊断轮 ｜ 车道：codex/doc-t5-inventory

## 1. 范围

本专题管「任务」这件事本身：任务分几类、各自的状态词与转移、启动／暂停／取消／恢复的入口、失败转人工、自动流程（三虎自动链＋各页面无人值守轮询）的推进与停点、重启恢复、进度展示位置、并发与排队。不管：各阶段做什么具体内容（那是各阶段册）、模型计费细节（专题六）、出错与日志（专题八）。

## 5. 给主控的问题建议

**Q1：全自动档要不要真的自动跑付费阶段？**
背景：切换文案写「付费或阻塞时会停下」，但 auto 档代码会打开 auto_asset／auto_video／auto_handoff 等无人值守开关，付费任务照常自动提交（§4-1）；semi 档则一定停下等确认。
- A 维持现状、改文案：代价最小，但用户看到「付费会停下」可能误判。
- B auto 档付费也停：与「全自动」语义更一致，但要改 approve／start_stage，且无人值守链路会停在付费阶段前，全自动不再「全自动」。
- C 付费自动单独设开关：三虎设置里加「全自动时代付付费步骤」一档，默认关。改动中等。
建议 C，理由：花钱是用户要握在手里的决定，给个明确开关比改文案或硬停都更直白；若主控认为现行为是设计，则至少选 A 修文案。

**Q2：在途（claimed）待办重启后的用户出口。**
背景：现在 claimed 项只在「运行状况」列出「要人工核实」，没有任何按钮可处置（#24）。
- A 维持只读：零改动，用户只能看日志自判。
- B 运行状况加「标记为已完成／标记为不再等」按钮：把在途项人工结清，仍不自动重跑。
- C 增加「重跑」按钮：对已核实未提交的在途项允许重跑，需先核实远端，风险最高。
建议 B，理由：与「在途＝要人工核实」的纪律一致，且不需要动远端语义。

**Q3：用户可见的任务中心要不要统一状态词？**
背景：五套状态对内部清晰、对用户不可见；「运行状况」弹窗只做只读投影，词仍是技术词（claimed／reconcile／late）。
- A 保持现状：内部口径不动，运行状况维持技术视图。
- B 在运行状况顶部加一层「人话汇总」（几个在跑／几个排队／几个要您处理）：展示层改动，不动状态源。
建议 B，理由：普通用户要的是「现在有几件事要我管」，不需要认识 claimed。

**Q4：失败→人工的路径要不要收口到一个入口？**
背景：现在失败的人工入口分散在三虎待确认项、运行状况、各阶段手动窗第四行、各页面导入按钮四类位置（#15）。
- A 维持分散：每处各管一段，不用改。
- B 运行状况的每条失败加「去哪处理」按钮（跳到对应页／对应窗）：把 RECOVERY_HINTS 的指引变成可点动作。
建议 B，理由：文档已经写好去哪补，让用户点得到比只写一句话更省事。
