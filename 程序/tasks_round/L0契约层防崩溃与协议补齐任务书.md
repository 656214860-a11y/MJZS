## 0. 总目标

让 L0 契约层的**承诺**与**运行时的行为**重新一致，并补齐 6 项缺失协议，使「启动崩溃」从「用户看到笼统 MessageBox」变成「可分类、可定位、可执行」。

1. **启动时跑契约自检**，失败分级（Fatal 拦住 / Degraded 警告继续），用户看得到是哪一类问题。

3. **契约文本不再给出错误指令**（`storyboard_contract` 的 `writing.py` 路径）。

#### 3b-1 抄 Spring Boot `FailureAnalyzer` → 复活 `error_codes`

**源码**：`org.springframework.boot.diagnostics` 包。

```java
public interface FailureAnalyzer {                    // 函数式接口
    @Nullable FailureAnalysis analyze(Throwable failure);   // 分析不了就返回 null
}
public class FailureAnalysis {
    private final String description;       // 发生了什么
    private final @Nullable String action;  // 用户该做什么
    private final Throwable cause;
}
```

关键在 `FailureAnalyzers.analyze()`：**按顺序遍历 analyzer，第一个返回非 null 的胜出**；每个 analyzer 的异常被 `catch (Throwable) { logger.trace(...) }` 吞掉——**诊断器自己崩了不能掩盖原始启动失败**。

**落地方案**（并入轮 3A 的 D3-d）：

```python
# contract/error_codes.py 增补
# 1) ErrorCode 加 severity 字段：fatal / degraded / recoverable / info
# 2) 加派发链
Analyzer = Callable[[Exception], 'ErrorCode | None']
def analyze(failure, analyzers: tuple[Analyzer, ...]) -> ErrorCode:
    for fn in analyzers:                    # 首个非 None 胜出
        try:
            hit = fn(failure)
        except Exception:                   # 诊断器崩了不能掩盖原错
            continue
        if hit is not None:
            return hit
    return lookup('E-UNKNOWN')
```

**为什么值得**：实测 `error_codes` 全仓仅 5 个文件引用（自身、`http_client.py`、2 个测试、`_layers.py`）——这就是「近乎死码」的量化证据。加 `severity` + 派发链后，错误码表从「字典」变成「路由器」，才有调用点。成本约 60 行，零新增 import。

#### 3b-3 抄 Flyway 版本阶梯 → 改造 `artifact_schema.migrate()`

**Flyway 机制三句话**：① 每次迁移是带版本号的不可变文件；② 执行记录写进历史表；③ 校验 checksum，历史文件被改过就报错。

```python
STEPS = {

# while current < target:
#     payload = STEPS[kind][current + 1](payload); current += 1
```

`main.py` 实抓：

```python
    logging.error(f"ASSETS_STARTUP_FAILED: {kind}\n{message}")

def database_failure_message(error, db_url):   # 固定类别码 + what + fix

    failure = "locked"          # fix = "Close any program that has it open…and start again."
```

**为什么替换 3b-1**：Spring Boot 的 `FailureAnalyzer` 是**接口 + 遍历 + 首个非 null 胜出**，那套复杂度是为「上百种异常类型的框架」设计的。ComfyUI 的 `kind` 枚举 + `what`/`fix` 三元组是**同一思想的最小可用形态**，且 `kind` 是固定闭集——单进程 Tkinter 直接可移植。3b-1 的 `analyze()` 派发链保留（它解决「多个 analyzer 按序匹配」），但**失败类别的表达**改用 ComfyUI 的 `kind`。

```python
# Diagnostic 增加两个字段，与 ComfyUI 同构
Diagnostic(severity, scope, code, message, remedy, escape_hint)
#   message  ← ComfyUI 的 what（发生了什么）
#   remedy   ← ComfyUI 的 fix（怎么办）
#   escape_hint ← ComfyUI 的 WITHOUT_ASSETS（一条逃生通道，可空）
```

**不抄的部分**：ComfyUI 是 `sys.exit(1)` 后由外部启动器匹配 `ASSETS_STARTUP_FAILED:` 日志行。本项目是 `.pyw` 双击直启，**没有中间启动器**——要抄的是「类别码 + what + fix + 逃生」四段信息结构，不是「打日志然后死」这个动作。本项目走 `MessageBoxW`。
