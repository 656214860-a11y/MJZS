## 先修正 R1610 的表述

R1610 Q7 原文写"仓库无 coverage 工具与阈值"——**阈值此前确实没有**，但"覆盖率审计"这一名目下已有 `test_coverage_audit_ratchet.py`；该文件审的是**动态导入／平台调用／事件 kind 等静态谓词台账**，与"行覆盖"无关，两者不能互相顶替。本轮新增的是行覆盖度量，不动既有审计棘轮。

## 实现

1. **工具 `scripts/coverage_report.py`**（零第三方依赖，不进分发包）：
   - 口径：生产运行时模块集合 = 递归生产 .py 去掉 `skills/`／`scripts/`／`reference/`／`outputs/`／`附加工具/` 与测试／自检器，与 `tests/architecture/_scan.production_runtime_files()` 一致（本轮 270 个）。
   - 采集：`sys.settrace`＋`threading.settrace` 只对生产模块记行事件；**为什么不用 `trace`**：随附解释器 Python 3.15.0a2 未随附标准库 `trace`（`import trace` => ModuleNotFoundError），coverage.py 亦未安装且不得引入运行时依赖。
   - 采集范围含目标用例的**导入期**执行（与 coverage.py `--source` 口径一致），故套件加载在 tracer 生效之后。
   - 退出码：目标用例全通过＝0；存在失败／错误＝1 且**拒绝写基线**（避免把退化后的数字当基线）。
2. **基线 `维护记录/覆盖率基线.json`**：8 个核心定向目标（金额不变量／请求台账／首帧生命周期／视频生命周期／后台任务队列／生命周期通用／发布恢复／队列认领），实测 46/270 个生产模块被触及、46 条记录。
3. **门禁 `tests/architecture/test_coverage_baseline.py`**：①基线结构自洽；②登记模块都存在、且集合与生产运行时口径**相等**；③核心路径下限；④子进程真跑工具并断言采到 ≥1 条生产行且模块总数与基线一致。

## 诚实边界（不得当成"CI 有了覆盖率门禁"）

- 门禁**不重跑测量**：阈值只对基线里记录的那次测量成立，**发现不了"代码改了但没刷基线"的退化**；刷新基线必须重跑工具（8 目标约 14 秒），工具在目标用例失败时拒写。
- 46/270 是**8 个定向目标**的结果，不是全仓覆盖率；分母含大量 UI／桌面模块（定向用例本就不该覆盖）。因此本轮**不设全局百分比阈值**，只对核心路径设下限，避免用无意义的分母刷数字。
- 覆盖率只说明"行被执行过"，不说明断言有效（Q6 的 `price()` 缺陷就是行覆盖到了却算错的例子）。
