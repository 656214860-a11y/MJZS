## 3. 分轮任务

### 阶段 A：上下文窗口权威统一（立即可做，零外部依赖）

#### 轮 A1 —— 上下文超限识别与自愈

**目标**：服务端说「上下文超限」时，用户看到可操作原因，且系统自动纠正该模型的窗口。

**范围**
- `infra/model_router.py::error_class()`（`:176-187`）新增第 6 类 `context_overflow`
- `infra/model_router.py::failure_policy()`（`:190-209`）对 `context_overflow` 标记不可重试 + 可操作建议
- **观测记录（替代原「自动回填」，见下方改写说明）**：识别到 `context_overflow` 时，把**观测证据**写入该模型的 `context_probe` 字段，**不写** `context_length`

**识别词表**（中英并收，覆盖主流 provider 措辞）
```
context_length_exceeded / maximum context length / context length exceeded
prompt is too long / too many tokens / reduce the length
超出上下文 / 上下文过长 / 超过最大长度
```

**注意**：`error_class()` 现有 `'400' in text → protocol`（`:183`）会把上下文错误吞掉。新分支**必须排在 protocol 分支之前**。

> ### ⚠ 自愈方案改写（V2，原方案已作废）
>
> **原方案**：识别到超限后，按失败请求的估算 token 数「按保守比例回填」`context_length`。
>
> **为什么作废**：一次请求被拒，**只能证明该请求不被接受**，不能反推出真实窗口。真实窗口可能大于该请求量——被拒的原因也可能是 `max_tokens` 与输入叠加超限（假设 H3）。把估算值写进权威配置字段，正是本任务书要消灭的「把不知道伪装成知道」。
>
> **替代方案**：分「记录」与「采用」两段，中间插入人工确认。
>
> | 阶段 | 动作 | 写入位置 |
> |---|---|---|
> | 记录 | 存**观测事实**：失败请求的估算 token 数、时间、服务端原始摘要、模型名 | `context_probe`（**新字段，非 `context_length`**） |
> | 提示 | 界面提示「该模型曾拒绝约 N tokens 请求，请核实窗口并填 `context_length`」 | 用户可见 |
> | 确认 | 用户或受权维护者填入 `context_length` 后才生效 | `context_length`（保持唯一权威） |
>
> **`context_length` 的写入仍然只有一个入口**：人工/文档确认。程序**不得**自动写它。
>
> **`context_probe` 的用途限定**：只用于提示与诊断，**不得**参与预检判定。否则等于把猜测换了个字段名。
>
> **唯一允许的自动收紧**（保留）：若已有显式 `context_length` **且**观测值明确小于它，则把 `context_length` 下调到观测值——这是「用观测推翻已知的更乐观配置」，方向安全。**必须**写日志记录改前改后值，且**仅降不升**。

**验收**
- 新增 `tests/test_model_router_context_overflow.py`：5 条服务端措辞样本 → 均返回 `context_overflow`；`failure_policy` 判不可重试
- **`context_probe` 只记录不参与判定**：构造超限 → `context_length` **保持不变**，`context_probe` 有记录，提示可读到
- **自动收紧仅在「有显式值且观测更小」时发生**：构造该场景 → 值下调且有日志；构造「无显式值」场景 → `context_length` 仍为空
- 冒烟 8/8

**风险**：低。只加分支，不改既有分类。
**回滚**：单文件 revert。

**做法**（Q11 选项 ②：抽表 + 契约 + 登记测试）

2. **立契约**：定义 `StageHandler` Protocol，生命周期
   ```
   start(ctx) / pause(ctx) / resume(ctx) / cancel(ctx) / progress() -> dict
   ```
   每个已登记 handler 必须显式满足；阶段不适用的方法显式 `NotImplemented`，不得缺失。
3. **登记测试**：遍历 `pet_bus.STAGES` 全部阶段，断言每个都
   - 在 `STAGE → handler` 字典里有一项
   - handler 覆盖 Protocol 全部生命周期方法
   漏一项即红。
4. **扩展点文档**：在 `architecture.md` 给出「新增第 N 阶段需改哪几处」的确定清单，并由登记测试保证清单与代码一致（与 C5 的生成机制合并实现）。

**「保留入口」的验收标准**：新增一个阶段 = **改一份数据 + 实现一个 Protocol**，不需要改任何 `if/elif` 分支，不需要动 L3 之外的层。这条须写成测试（构造一个假阶段，断言不改核心代码即可登记并通过登记测试）。

**明确不做**：目录扫描自动注册的完整插件机制。理由：13 个阶段全在核心代码里，做全自动插件要同时写加载器和旧阶段适配，两头动、风险最大；而「保留新阶段入口」的目标用上述 ①–④ 已经达成。

## 12. 任务书书写标准规范（V2 新增，**即刻生效**）

本节是任务书格式的**唯一权威**。与 `runbook.md:274`（任务书须含的章节）配套：本节补充「怎么写才能被模型正确执行」，不重复其章节清单。

### 12.1 三项已确认原则

| # | 原则 | 含义 |
|---|---|---|
| **P1** | **执行契约，不是建议** | 任务书进入「可执行」状态前必备字段齐全；草稿可残缺。模型可提补充，**不得**把假设自行升级为已确认决策 |
| **P2** | **试点先行，不整批迁移** | 新规范先用一个真实变更包跑完整流程（编写→校验→执行→交接→归档），旧文档先索引、触及时再迁 |
| **P3** | **完成分四态** | `已实现` / `已验证` / `已合入` / `已发布` 分开记录；归档前核对目标态与遗留项，**不得**用单一勾选代替 |

### 12.2 事实与假设必须分栏

**这是本任务书 V1 最大的缺陷**：把推断写成「全部已核实」。

- **§0.1 已核实事实**：每条必须有可复现的证据坐标（文件:行号 / 命令输出 / git 对象）
- **§0.2 待证假设**：每条必须写「缺什么证据」+「取证方式」+「未取证前不得宣称什么」

**硬规则**：待证假设**不得**出现在「验收」条款里作为依据；依赖假设的实施项必须声明「该能力不依赖假设成立」。

### 12.3 依赖图与排程分离

- **依赖图**只放硬边，每条硬边须解释「为什么是硬约束」
- **排程**单独写，标注「软建议」
- **禁止**在依赖图里使用会被读成传递依赖的连线；确认无环（`A→B→A` 是严重错误）

### 12.4 每轮必填字段

| 字段 | 要求 |
|---|---|
| `目标` | 一句话，可判定是否达成 |
| `范围` | 精确到文件:行号或函数名；不写「相关模块」 |
| `前置` | 依赖哪一轮或哪条门禁；无则写「无」 |
| `验收` | **行为断言**，不写「正确实现」这类不可判定表述 |
| `风险` + `回滚` | 可执行的回滚动作，不写「视情况」 |
| `车道` | 属本车道 / 交接对象；写清占用文件归属 |

### 12.5 授权边界

- 涉及他人车道的合并，必须有**门禁表**（谁提供、怎么核），不得仅凭「提交存在」推断「验收完成」
- **不得代填**他人的验收勾选表——那需要对方自己的证据
- 阻塞时记录「阻塞于哪一条门禁」，不擅自代做
