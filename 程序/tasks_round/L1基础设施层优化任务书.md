## 0. 总目标

让 L1 基础设施层的**承诺**与**运行时行为**重新一致，消除三类问题：

1. **静默失效**——限流、计量、预算三处「代码看起来做了，运行时没做」。
2. **无界增长**——台账、缓存、诊断文件、内存队列四处只增不减。
3. **丢失更新**——五处「读—改—写」无跨进程互斥，双开即丢数据。

**不追求**：性能重构、模块拆分、依赖扩张。本轮以「止血 + 可验证」为准。

## 3. 缺陷清单

### P0 — 资损与用户可见故障

#### P0-1 限流器三处缺陷（`infra/api_endpoints.py`）

| 位置 | 缺陷 | 后果 |
| --- | --- | --- |
| `:101-109` `_RateBucket.wait` | `self.next = now + wait + self.interval` 是读改写，调用点在 `:132` **锁外** | 并发时两线程同得 `delay<=0`，限流失效 |
| `:137`、`:161` | `time.sleep(min(delay, RETRY_MAX_SECONDS))`，而 `RETRY_MAX_SECONDS = 3.0`（`:92`） | `interval = 60/rpm`，**rpm<20 时限流退化为固定 3 秒一发** |
| `:153` | `if bucket is None or abs(bucket.interval - interval) > 1e-9: bucket = _RateBucket(rpm)` → `:104` `self.next = 0.0` | 同 host 两模型不同 rpm 交替请求时**每次重建桶**，永不等待 |
| `:194` | `min(int(retry_after), RETRY_MAX_SECONDS)` | 服务端 `Retry-After: 60` 被截成 3 秒 → 必再 429 → 熔断 |
| `:196` | `hash(str(attempt)) % 100` 抖动是确定性的 | 惊群未消解，并发重试同相位 |

**优先级说明**：`rpm<20` 是生图/写实类供应商的常见配置，这条最容易被误判为「供应商限流严格」。

#### P0-2 重放叠加（`infra/pet_llm.py` + `infra/model_metering.py:77`）

```
REPLAYABLE_RETRY_STATUS = (0, 408, 409, 425, 429, 500, 502, 503, 504)
```

含 `0`（本地超时/断连）。叠加链：传输层重放 3 次 × `pet_llm` 的 Pro→Flash→兜底 3 层 = **最多 9 次付费 POST**。

**核心问题**：超时**不等于**服务端未受理。当前口径把「可能已计费」当「可安全重放」。

#### P0-3 计量预留泄漏（`infra/model_metering.py:16-43`）

```python
20:     try:
21:         result = send()
22:     except Exception:
23:         ledger.settle_model(request_id, {})
...
27:         raise
28:     usage = usage_of(result)          # ← 在 try 之外
29:     if on_result is not None:
30:         on_result(result, usage)      # ← 在 try 之外
31:     if hasattr(ledger, '_find'):
34:         record_request_attempt(...)   # ← 在 try 之外
42:     ledger.settle_model(request_id, usage)
```

`try/except` 只包住 `send()`。`:28`／`:30`／`:34` 任一抛错即跳过 `:42`。

**后果**：预留额度永久停在 `reserved` → `budget.reserved_amount` 单调上涨 → **最终所有后续请求被预算拒绝**，而账单无任何超支记录。这是「越用越不能用」型故障。

> 已确认：`:22-23` 的 `except` → `settle_model(request_id, {})` 是对**发送失败**的正确处理，本缺陷是它之外的残留缺口，不推翻既有设计。

#### P0-4 台账锁争用即报错（`infra/request_ledger.py:315-332`）

```python
330:                     msvcrt.locking(stream.fileno(), msvcrt.LK_NBLCK, 1)
331:                 except OSError:
332:                     raise ValueError('请求台账正在更新，请稍后重试') from None
```

`LK_NBLCK` 非阻塞、无重试。正常并发（8 路并行自检、双开实例）被当成用户可见错误。

**正例**：`infra/clipboard_lock.py` 已有正确写法——`hold(timeout=30.0, poll=0.02)`（`:33`）→ `_acquire(timeout, poll)`（`:54`）→ `deadline = time.time() + max(0.0, float(timeout))`（`:62`）+ `while True`（`:63`）+ `if time.time() >= deadline` 才放弃（`:77`）+ `time.sleep(poll)`（`:79`）。同仓库两个口径。**v2 修订**：结构照此，但期限改用 `time.monotonic()`，且轮询须在 `_REQUEST_LOCK` 之外（见 L-N3 与轮 1 的 R1-j）。
