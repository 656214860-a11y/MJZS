## 预览隔开了什么

1. 应用数据：config.json、projects.json、desktop_settings.json 都建在数据目录的 `app` 下，项目库位置（downloads_root）也指在数据目录里，里面只有一个空的示例项目；不建 private，不复制任何密钥、登录状态或设置。数据目录不能放在代码仓库里，不是本工具建的非空目录不用也不删。
2. 已有数据复查（`_check_stays_inside`）：已建过的预览数据再用之前，项目库位置缺失或指到数据目录之外、登记里有数据目录之外的项目，都拒绝启动并提示 `--reset`。原因：应用的 config.json 里没有 downloads_root 时会退回写死的默认项目库，也就是用户真实的那一份。
3. 只在车道里开窗口（`in_linked_worktree`）：主工作区的 `程序` 目录同时放着正式应用的数据，按代码目录找文件的模块会碰到它，所以在那里拒绝开窗口（`--print-only`、`--reset` 不受限）。
4. 用户级目录（`isolate_user_env`）：开窗口前把本进程的 LOCALAPPDATA、APPDATA、USERPROFILE、HOME、HOMEDRIVE、HOMEPATH 改指到数据目录的 `user` 下，并去掉名字像密钥、令牌的环境变量和几个「配置目录另有所指」的覆盖项（只看名字，不读取值）。预览里没有登录、没有模型密钥。
5. 注册表（`block_registry`）：应用读写注册表都经 `contract.platform_tools.windows_registry()`（开机自启、登录时钟基线、「下载」文件夹位置），预览进程里把它换成返回 None，各调用方本来就把 None 当「本机不支持」。
6. 关窗清理（`block_exit_cleanup`）：应用按自己的路径关窗时，`ui/desktop_lifecycle.py` 的 `finish_close` 经 `orchestrator.exit_maintenance.launch_cleanup` 另起三个后台进程（项目库清理、日志清理、仓库卫生）。预览进程里把这个派发入口换成只打印一行的空操作。按名字搜过：三个清理的启动函数在产品代码里只有 `exit_maintenance` 调，`exit_maintenance.launch_cleanup` 只有 `finish_close` 调。

还共用的：系统临时目录里的缩略图缓存；PATH 不动，本机装的命令行助手和工具链仍能被找到，只是没有登录；`agent/prompt_optimizer.py` 按代码目录的 config.json 找提示词优化工具的位置，车道里没有这份文件时用写死的默认位置（只用来找工具）；网络照常，试跑里看到启动时向应用服务端的 `/v1/meta` 发了一次 GET（经本机的系统代理），标准库为此读了系统代理设置（注册表只读，不经应用的注册表入口）；车道代码目录里的 `outputs\publication-transactions`（含 `writer.lock`）和 `logs` 照常会写，它们不进版本库。

## 如实说明

- （一）隔离的依据有两样：按入口读代码（应用数据目录、用户级目录、注册表入口、关窗清理、项目登记的几条路径），加上改前改后各一次带记录的试跑。记录用的是 Python 的审计钩子（一次性脚本，放在仓库外的 `.agent-tmp/ccc4a5fe_preview_audit.py`），只看得到预览进程里 Python 这一层的文件打开、建删改名、注册表、进程启动和网络连接；原生代码自己做的文件访问（比如界面库）和子进程里发生的事看不到。两次试跑里起过的子进程只有读分支名的 git。试跑只是启动、停留 25 秒、关闭，没有在窗口里点任何东西。
- （二）关窗清理这一处是读关窗路径时发现的，改前的试跑证实了：预览窗口关闭时应用去起项目库清理进程。`infra/storage_maintenance.py` 的 `downloads_root()` 读的是代码目录里的 config.json，不是注入的数据目录；车道里没有这份文件，就退回写死的默认项目库。改之前这个子进程其实起不来：它的工作目录是预览的数据目录，那里没有 `infra` 包（在一个不相干的目录下验过，找不到这个包）。那是碰巧挡住的，不是设计，所以改成预览进程里明确不派发。
- （三）已有数据复查挡的是以后的变化：按现在的代码，项目只会登记在项目库位置下面（新建、重建登记、找回缺失项目三条路径），界面上也没有改项目库位置的入口，预览窗口自己走不到数据目录外面。这一点只读了代码，没有在窗口里逐个点过。待做的项目库位置设置（UX-D2B、FIX-P1）合入以后，这条复查才真正用得上；到时要再看一遍预览里能不能把项目库改到外面。
- （四）「复制真实项目来预览」拿掉了：真实项目的 config.json 里记着指向原项目的绝对路径（episode_dir、episode_file），原样复制后预览会顺着这些路径读写原项目。初稿里那部分代码留在仓库外的草稿目录，补上路径改写和残留检查后另开一项。所以现在的预览只有一个空的示例项目，只能看界面和交互，不能真跑模型。
- （五）子进程用例 `test_isolated_window_starts_and_closes_in_a_child_process` 是这批用例里唯一照 main 的顺序把隔离全做一遍再真起窗、真关窗的；它盯的是「关窗期间没有进程启动」，去掉一行的核对证实它会红。另一条起窗的用例 `test_window_title_carries_preview_prefix` 在测试进程里直接起窗，不做隔离，1.5 秒后直接销毁窗口（不走应用的关窗路径），和仓库里别的界面用例是同一种写法。子进程用例用「窗口已不存在」判断应用自己关掉了窗，没有验证关窗过程里的每一步。
- （六）排查时查到、不属于本轮的两处，已在心跳里提醒各窗口，另行登记：其一，在车道里不注入数据目录直接起应用再按应用的路径关窗，第（二）条说的清理会用没合入的代码去清理默认项目库（读代码得出，没有实际触发过，也不打算触发）；其二，应用启动约 9.5 秒后把技能目录同步到用户主目录下的 `.codex/skills`、`.claude/skills`、`.agents/skills`，测试运行器没有改指用户主目录，车道里活过 9 秒的真实窗口可能把车道版本的技能同步进真实主目录（预览里这些目录已改指，试跑看到它们写在数据目录里；真实主目录那一侧没有实测）。
- （七）过程里的失误：其一，我跑了 `run_selftests.py --help` 想看选项，它不是帮助选项，而是跑了一次 0 个文件的定向测试，刷新了各车道共用的增量台账，并给「最近 5 轮自检中位基线」加了一个 0 秒样本；没有影响任何测试内容，5 轮后自然冲掉。其二，有两次在内容还没定稿时就起了架构门禁（22:33 那次中途停了，22:36 那次跑完是绿的但内容后来又改了），上表写明了哪一次对应最终内容。其三，改后那次试跑的输出文件里没有「关窗清理已关闭」一行：记录程序用不刷缓冲的方式结束进程，标准输出没写出来；那次试跑的依据是审计记录里关窗前后没有进程启动，这一行在子进程用例和去掉一行的核对里看得到。
- （八）先前「提交时由提交工具跑架构门禁」的理解不对：按代码，提交工具只做凭据扫描和点名测试，提交钩子只跑两个静态检查模块（tests.test_static_names、tests.architecture.test_static_hygiene），整套架构门禁要单独跑。这一条是读代码得出的。
- （九）结构登记撞车和挪基准：`governance/structure.json` 和基线文件头同时被另一条未合入的车道（EC-2，分支 codex/ec-catch-all）改着；基线文件头里记着登记表的哈希，两边各自生成就一定冲突，第一次提交被提交工具的重叠检查拒绝（原文见上表）。处理是把本车道快进到 EC-2 的提交 56e82144 之上，登记条目加在它那一条后面，基线重生成。这是验收窗口自己定的做法：提交工具给的两个办法里，「错开改动位置」对基线文件头做不到，「等对方合入后再提交」要多等一轮。代价：本分支带着 EC-2 的两笔提交（R4098、R4102），必须排在 EC-2 之后合入；EC-2 合入前如果又改了登记表，本分支要再挪一次。挪基准还把主干的 R4096（f624a5fc）带了进来，开工时的基准比它早一轮。挪基准之后第二次提交又被拒（原文见上表）：提交工具对同一轮次的重试只接受和上一次相同的 HEAD、命令和文件内容。照 R4070 结果文件里记过的先例，第三次改用提交工具不带文件参数的用法（先按路径暂存这七个文件，再提交已暂存的内容；重叠检查、凭据扫描、点名测试和证据仍由提交工具自己做），第一次留下的那份重试登记没有动。
