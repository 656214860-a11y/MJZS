# 全量测试优化计划

**创建时间**：2026-11-19  
**目标**：降低全量测试对开发进度的阻塞影响

---

## 📊 现状分析

### 触发频率问题

- **规则**：每 8 个改过源码的轮次触发一次全量
- **实际**：R2594 → R3633（最近一次成功全量）= **1039 个轮次**
- **当前**：R3633 → R3809 = **176 个轮次**，已积累 6 个源码轮次（接近阈值）
- **阻塞**：R3818 正在运行全量（已 10+ 分钟），所有会话排队

### 性能数据

从 `run_selftests.py` 注释：
- **并行模式**：约 **85 秒**（8 路并行，24 核机器）
- **串行模式**：约 **204 秒**
- **瓶颈**：Tk 界面测试（单例 3-6 秒，需要建 11 页界面）
- **优化历史**：已从 204 秒优化到 87 秒（第 25 期）

### 验收锁问题

- **锁范围**：全局锁 `.git/full-safe-selftest.lock`
- **影响**：所有会话（主工作区 + 工作树）全部阻塞
- **当前状态**：R3818 (pid 58892) 持有锁，已运行 10+ 分钟

#### 方案 B2：分层全量

**当前已支持**：
```bash
python run_selftests.py --layer architecture --all  # 只跑架构层
python run_selftests.py --layer service --all       # 只跑服务层（无 Tk）
python run_selftests.py --layer gui-short --all     # 短 Tk 测试
```

**实施计划**：

   - 改动 L4 → 只跑 `--layer gui-short + gui-e2e`
   - 跨层改动 → 跑完整全量
2. ⏭️ 定期（每周）跑一次完整全量作为基线验证

**效果**：
- 分层全量耗时：**20-40 秒**（而不是 85 秒）
- 大部分轮次只需分层全量

### 层次 3：去除验收锁阻塞 ⏭️ **中期可做**

#### 方案 C1：工作树级别验收锁

**问题**：全局锁阻塞所有会话

**改进**：
```python
# 当前：.git/full-safe-selftest.lock（全局唯一）
# 改成：每个 worktree 有自己的锁
# - 主工作区：.git/full-safe-selftest.lock
# - 工作树：.git/worktrees/<name>/full-safe.lock
```

**实施**：
1. 修改 `selftest_receipts.py` 的锁路径逻辑
2. 检测当前是否在 worktree（`git rev-parse --git-common-dir`）
3. 使用对应的锁文件路径

**效果**：
- 主工作区和工作树可以并发运行全量
- 只有同一个工作树的会话会互相阻塞

**风险**：
- 需要仔细设计锁粒度
- 并发全量会占用更多 CPU/内存

### 层次 4：按需全量而非定期全量 ⏭️ **长期优化**

#### 方案 D1：智能触发全量

**当前**：每 N 个轮次强制全量

**改进**：
```python
# 按改动范围决定
# - 改动"风险路径"（L0、L1、架构层）→ 立即全量
# - 改动"普通路径"（L2、L3、L4）→ 累计 8 个轮次后全量
# - 改动"文档"→ 不触发全量
```

**实施**：
1. 分析 git diff 的文件路径
2. 按路径判断风险等级
3. 动态调整全量触发条件

**效果**：
- 大部分轮次不需要全量
- 只有真正需要时才全量验证

#### 方案 D2：增量凭据复用

**当前**：全量必须跑所有测试

**改进**：
```python
# 按改动范围重跑
# - 只重跑改动模块的测试
# - 其他模块复用上次绿凭据
```

**实施**：
1. 分析 git diff 找出改动的模块
2. 找出受影响的测试（直接测试 + 间接依赖）
3. 只跑受影响的测试，其他复用凭据

**效果**：
- "增量全量"耗时：**10-30 秒**（而不是 85 秒）
- 只有"真正的全量"（定期基线验证）才跑完整
