文件名 R3812 是历史标签，不是有效轮次。执行时重新领取真实轮次。前置：[内建总控退役任务](总控机制删除任务书.md)通过验收；若由不同模型并行准备，只能调研，不得同时修改相同目录、Git 索引或登记文件。

## 1. 用户目标与已确认取舍

把文档统一到 docs，保留每个主题唯一权威；把目录规则写成机器可读、能阻止新增违规的团队协议。迁移账户设计全文，不再留到“以后再议”。

已确认：

- 保留 `程序/` 作为源码根，在治理声明中说明其承担 src 角色，不改启动器和全部 import。
- 不以本任务重排 contract/infra/domain/orchestrator/ui 等生产目录；技术层是依赖约束，未来新增目录优先按运行时或业务边界。现有布局作为显式接受的存量记录，不能宣称已满足业务模块分级。
- 测试保持现有位置；用可核对归属记录表达被测模块/契约，不做逐文件一一同名强制。按名筛选是否支持子目录应读运行器验证，不能用未经核实的说法论证。
- 新目录使用英文小写；自有代码/测试文件使用英文小写下划线；文档允许中文。既有标准入口名、ADR 编号、阶段编号与第三方原名按类别豁免。
- 禁止新建同一文档的日期/版本副本，版本放 Git 或正文。历史轮次文件、已冻结历史 ADR 和用户数据不受此命名规则改写。
- 先建规则与检测、跑现状基线，再迁移，最后验新布局。规则要检验新违规集合，不能只比较总数。
- legacy 只容纳经证明退役、仍有参考价值的内容，不做缓存/快照垃圾桶；有实际迁入对象时才创建。不删除 Git 历史、不把第三方总控包重新放入 legacy。

## 3. 统一文档目标结构

新增目录按真实内容创建，不为示意树创建空目录。以下是迁移职责，不是机械创建命令：

```
程序/
  docs/
    README.md                 文档唯一入口：按读者、任务和主题导航
    requirements/             PRD/SRS 与验收口径
    specs/                    七册设计规格；账户设计全文并入 07
    stages/                   阶段 REQ/DES，编号保持
    adr/                      现有架构决策，保持编号与唯一索引
    process/                  发布、运维与验收流程
    guides/                   用户操作说明
    contracts/                仍有效、未并入其他权威的独立契约
    records/                  工程文档登记、证据索引与迁移台账
  governance/
    README.md
    structure.json
    structure-baseline.json
    check_structure.py
    decisions/                仅存目录治理决策，不复制 docs/adr 决策
  legacy/                     有经确认的退役对象时创建
```

层级“2–4 层”以自有源文件所在目录相对治理根的深度计算并明确定义，不拿第三方技能资源深度、测试 fixture 或运行时项目目录反推违规。规则中写出精确计数方法。

### 3.1 说明目录逐项迁移

| 原文件/内容 | 目标职责 | 处理 |
|---|---|---|
| 产品需求规格.md | docs/requirements/ | 保持需求唯一权威；更新所有现行消费者 |
| 发布检查单、商用交付资料、制作失败与人工替代、存储盘点与保留、维护约定、版本控制处置说明、联调测试出口基线、每分钟成本核算 | docs/process/ | 修相对链接与节号，区别流程、历史证据、当前验收状态 |
| 编剧功能说明 | docs/guides/ | 标明实际适用版本，不冒充当前全部功能 |
| 工程文档登记表 | docs/records/ | 与 doc_registry 的输入路径和扫描范围一起迁移 |
| 已知坑与不可破坏契约 | docs/contracts/ 或现有权威明确指定落点 | 一份主题一份权威，更新 AGENTS/导航/测试中的指向 |
| 模型金额预算 | docs/contracts/ | 属费用契约，不因名字当作历史记录 |
| 生成服务失败处理契约 | docs/contracts/ | 保留适配器行为契约与测试映射 |
| 更新记录 | 原位置存在 CHANGELOG 时优先核查主题重复 | 合并当前有效条款到唯一更新记录；不能未经比较直接删 |
| 账户会员云端设计 | specs/07 账户域 | 全文合并见 §4，不新建第二个 account 设计目录 |
| 账户会员云端立项前清单 | specs/07 决策台账或 docs/records/历史立项记录 | 已定结论合入权威；待决项保留 ID 和状态；历史不冒充现行设计 |
| 已并入设计规格 | docs/records/迁移台账 | 逐条校正旧目标与失效链接，不保留空泛指针冒充兼容入口 |
| 说明/示例/雨夜修伞/ 全部 md/json/媒体 | 先核查运行时消费者与分发清单 | 用户演示资源须在运行时资源/示例包保留，不得随开发 docs 排除出包；说明可在 guides 引用 |
| 总控包脚本机检桥边界 | 前置任务已删 | 不重新创建 |

`说明/` 清空前列出全量剩余项；任何未列项先归类。必须证明没有漏掉非 md 文件与示例资源，才删除空目录。

## 5. 机器可读目录协议

### 5.1 structure.json 必备字段

使用 JSON，不引入新运行依赖；具体 schema 由执行者编写并在 README 解释：

| 字段 | 必须表达 |
|---|---|
| schema_version / root | 协议版本、明确相对仓库根或程序根，禁止混用 |
| roles | 自有目录角色、职责、允许内容、运行时/开发期归属 |
| owners | 每个纳管目录的责任角色与交接方式；不要虚构多人团队 |
| naming | 代码/测试/文档/ADR/标准入口/历史任务/第三方分类规则 |
| depth | 深度计算定义、目标 2–4 层、纳管与排除范围 |
| test_ownership | 模块测试与跨模块契约测试的可解释归属，不强制所有文件同名 |
| excludes | user/runtime/private/cache/build/vendor/gitlink/worktree 边界 |
| packaging | 构建中间产物与发布产物归属、签名配置单一位置、禁止纳入分发的目录 |
| retirement | 删除/归档/legacy 的判据、审批证据与去向 |
| exceptions | 精确路径、理由、owner、复核条件；不接受无限通配豁免 |
| baseline | 旧违规指纹集合、来源提交/清单摘要；新违规即红 |

保留 `程序 ≡ src` 角色映射；不是声称源码所有二级目录已按业务域划分。

### 5.2 检查器

- [ ] `governance/check_structure.py --check` 只读，输出结构化违规与可读摘要，退出码准确。
- [ ] 只枚举 Git 跟踪文件与明确指定的新文件候选；忽略 `.git`、工作树、用户项目、private/data/logs/outputs、虚拟环境与第三方包内部。
- [ ] 不 import 产品 UI、不连接网络、不初始化/下载 git submodule、不读取凭据正文。

- [ ] 基线生成必须显式 `--write-baseline`，输出差异，禁止检查模式静默刷新或自动放宽。
- [ ] 比较违规身份集合，而非数量。例如删一个旧违规后新增另一个违规，仍须失败。
- [ ] 空目录只检查实际自有源码纳管目录；Git 不跟踪空目录，不能扫描运行数据空目录后要求用户删除。

## 6. 打包、签名配置与 legacy

- [ ] 比较共享 .gitignore 与本机 .git/info/exclude。outputs 仅本机忽略的情况必须给可共享规则；新增 dist/build/安装器中间目录的精确忽略规则。
- [ ] 禁止直接用 `*.exe`、`*.zip`、`*.pyd` 全局忽略替代归属设计：必要二进制/fixture/vendor 可能需要跟踪。先盘点既有规则与副作用，再限定产物路径。
- [ ] 区分 Git 忽略与分发排除，两套规则都验证；忽略某路径不等于不会进入安装包。
- [ ] 安装器/签名/SBOM 配置集中管理。若当前无真实配置，只在协议指定未来落点（例如 packaging），不先建空目录、不在本轮实现安装器。
- [ ] 签名私钥/证书凭据不得迁入治理目录，禁止把私钥放仓库当作集中管理。
- [ ] `h3_launcher.pyw` 先确认确实退役且无用户入口，再决定迁入 legacy。
- [ ] `reference/HoLLMwood` 是 gitlink，不能整个 reference 直接移动/删除；逐项确认消费者、许可证与子模块元数据，再按 Git 子模块流程处理。仍活跃的参考库保留原归属。
- [ ] legacy 仅实际有对象时创建，带 README/来源/退役理由/最后适用版本/无运行依赖证明；不是“永远不能删除”的历史仓库。
- [ ] 检测生产依赖不只查静态 import，还检查动态注册、脚本路径、资源清单与打包入口。
- [ ] tests 应禁止运行 legacy 源码，而非完全不看 legacy：结构门禁仍须检查其隔离与不进分发。

## 7. 迁移执行顺序

1. 独立工作树、领号、读规则、记录旧目录/引用/内容摘要/测试基线。
2. 建协议与只读检查器，用坏样本证明能红，再冻结当前精确违规集合。
3. 先完成账户设计全文合并及条款映射，避免迁移后再保留重复权威。
4. 按角色逐组 git mv 文档与示例资源；每组同步工具路径、相对链接、正文节号和登记表。
5. 处理已确认的 legacy 对象、打包归属与共享忽略规则。
6. 迁移完成后检查新增违规、失效引用、条款丢失、示例出包和用户数据边界。
7. 输出真实结果与任务完成文件，按项目提交/合并协议交付，不绕锁不覆盖他人改动。

## 9. 退出与回滚
