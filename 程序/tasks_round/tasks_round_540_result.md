# R540 性能/资源轮结果

## 方案选择与改动

选择方案 A（延迟构建），未选方案 B：Tk 控件及页面构造只能在主线程执行，后台构建会引入线程不安全的 UI 调用。

`desktop.py` 原本在启动 150ms 定时器中直接调用 `choose_project()`；当记住当日项目时，它会同步进入 `load()` 并构建剧本准备页。本轮把该定时器改为 `_choose_project_after_first_paint()`：

1. 150ms 到期只写入“正在打开今日项目…”状态；
2. 通过 `win.after_idle(self.choose_project)` 让 Tk 先处理首窗绘制；
3. 再沿用原有 `choose_project()` / `load()` / `show(0)` 构建同一页面。

不改页面最终样子、项目打开逻辑、其他页面或任何用户项目数据。新增
`tests/test_ui_edges.py:47-70` 回归，验证启动回调必须登记 idle 的项目选择，而非直接构建。

## 启动测量

条件：项目内置 Python、同一已记住项目、仅注入内存计时钩子，运行 3 秒后自动关闭；不写回旧实现。

| 指标 | 旧：150ms 后直接构建（内存模拟） | 新：首帧后 idle 构建 |
| --- | ---: | ---: |
| 主窗口映射 | 0.440 s | 0.449 s |
| 内容构建开始 | 0.615 s | 0.631 s |
| 内容构建完成 | 1.761 s | 1.864 s |

结论：R539 已移除递归 SKILL 扫描后，旧流程也已在内容构建前映射窗口；本轮测量差异处于本机启动波动范围，不能声称加速了页面构建。此改动将“先首帧、后重建”的启动体验显式固定，避免未来把同步项目加载重新放回首窗绘制前。
