## 2. 问题

原门禁（R2611 起）把暂存路径与每条带工作树的分支「相对 master 的改动清单」求交集，有交集就拒绝提交。它不看对方是否还在动，也不看两边改的是不是同一处。

- 仓库现在有 84 条带工作树的分支（不计主干和本分支），46 条在 24 小时内有提交或心跳，51 条已经没有领先主干的提交。`architecture.md`、`runbook.md` 这类公共文档有十几条分支改过，任何一轮碰它们都会被拒。
- R3919、R3922、R3950 三轮被拒后都绕开了提交工具（任务书 F8；R3950 结果文件 §5）。
- 本轮自己的暂存内容按原口径与 19 条分支重叠，原门禁拒绝（§4.3）。
- 原门禁逐条分支串行读改动清单，在这个仓库上每次提交要等约 11 秒（§4.4）。

## 3. 现在的规则

`branch_scope.commit_gate_report` 返回 `conflicts`（非空即拒绝）、`notes`（只提示）、`skipped`（没比对成，只警告）。

| 情况 | 结论 |
|---|---|
| 双方都新增了同名文件，对方车道活跃 | 拒绝（内容相同也拒绝） |
| 与活跃车道路径重叠，三方试合并在这条路径上出现新的冲突段 | 拒绝 |
| 同上，但冲突落在改名后的路径上（有一方移动或改名过文件） | 拒绝 |
| 路径重叠，试合并能自动合并 | 提示 |
| HEAD 与对方此前就冲突，暂存后每个冲突段都与此前某一段逐字相同 | 提示 |
| 新冲突来自对方分支带着、本分支还没有的主干提交 | 提示「合入前需要先变基」 |
| 对方车道超过 24 小时没有提交也没有心跳 | 提示 |
| 改动清单读不出来、试合并没做成 | 警告，不拦截 |

- 车道：`git worktree list` 里带分支的工作树，排除主干和当前分支（没变）。分支尖已经在 master 历史里的车道不再逐条读改动清单。
- 活跃：分支最新提交或 `lanes.json` 的 `last_seen` 在 24 小时内。活动时间读不到的按活跃算。
- 试合并：`git merge-tree --write-tree`，合并基取 HEAD 与对方分支尖的合并基，一边是暂存树，一边是对方分支尖。「是不是本次新增」靠再做一次 HEAD 树对同一分支尖的试合并来比，比的是每个冲突段的内容指纹。
- 改名按「删旧名加新名」两条比对（暂存区和对方的改动清单都是），这样对方改过名的旧路径也算重叠。
- 试合并在临时对象目录和索引副本上做，不往仓库写对象，不锁、不改索引。
- 结果按（树、合并基、分支尖、路径）缓存在 `<git common-dir>/scope-gate-cache.json`，最多 500 条，删掉只是下次重算。
- `dev.py commit` 把提示打印到标准错误。`python 维护记录/基准脚本/branch_scope.py --staged` 可以在提交前先看结论，会被拒绝时退出码 5。

## 5. 取舍与已知边界

1. **试合并没做成只警告，不拦截。** 与这个模块原有的做法一致（改动清单读不出来的分支本来就只警告）。代价是 Git 出故障时门禁等于没有，警告行会写明哪条分支、哪些路径没比对。
2. **「此前已冲突」按冲突段的内容比。** 改动落在已有冲突段里面、或紧挨着它使得这一段变长时，按新冲突拒绝，这是偏严的一侧。文件正文里本来就有以 `<<<<<<< ` 开头的行时，分段会切错；两次试合并切法相同，结论仍然偏严。没有冲突标记的冲突（改对删、二进制）按整份内容比。
3. **改名只覆盖 Git 能认出来的文件改名。** 对方把整个目录改了名、本分支在旧目录里新增文件，这种情况路径没有交集，门禁不会去试合并。这是按代码推断的，没有写用例验证。
4. **「与主干新提交冲突」的判断假定主干叫 `master`**（这个模块一直如此，改动清单用的就是 `master...<分支>`）。判断不了时冲突仍算在车道头上，偏严。这类冲突只提示不拦截：门禁管的是车道之间，与主干的冲突在合入变基时处理。
5. **超过 24 小时没有提交也没有心跳的车道只提示。** 任务书定的口径。有人在这样的车道里改了很久却没有提交，双方会在合入时才撞上。
6. **语义冲突查不出来**，由合入时的出口检查兜底（任务书已写明）。没有工作树的分支不比对（没变）。
7. **缓存并发写**：读、合并、原子替换，不加锁。两个提交同时写会丢掉其中一方的新记录，后果只是下次多算一遍。
8. **`staged_files` 的返回值变了**：改名现在返回新旧两个路径（原先只有新路径）。调用方只有本模块。
