# 产物命名盘点（NAMING-INVENTORY，R4196）

> 只读盘点＋设计稿，不改产品代码。调研基准 `6e687b94`（分支 `codex/naming-inventory`）。
> 卡面出处：用户 2026-11-22 前后（HALF-01）——「统一文件命名『类型＋provider＋年月日』，适用于应用输出的任何文档」。
> 本文所有「现状」均给出 `文件:行号`；示例项目名统一用虚构名「星河」，不使用任何真实项目数据。
> 标注「未核实」的条目表示本卡范围内没有读到决定性代码，不能当作结论。

## 1. 范围与方法

- 盘点对象：应用在**用户项目目录**与**程序目录**里写出的文件，按类型分行列表。
- 只读范围按卡面：路径权威模块（`stage_layout`／`storyboard_paths`／`script_contract`／`asset_contract`／`model_pool.env_file`）、`*_manifest`、`*_lifecycle`、`stage_completion_service`、各阶段续跑台账；另为回答「谁从文件名反解信息」扩展到命名生产方与目录扫描方（`file_naming`、`file_index`、`storage_maintenance`、`artifact_lineage`、目录服务）。
- 不在范围：`程序/private`、`.env`、`*.dpapi`、`outputs`、`logs`、用户真实项目目录的实际文件名（禁止扫描）。
- 已有相关结论：`docs/specs/09_资产数据生命周期.md` §5（第 69–78 行）已列资产图三条入库路命名并标「统一规则待定」；§13 Q1（第 172 行）仍 ❓ 未决。本卡把其余类型补齐，并把 Q1 并入第 8 节待裁决题单。

## 2. 命名权威总览

应用内文件名不是各处手写，而是收口在少数几个模块：

| 权威 | 位置 | 职责 |
| --- | --- | --- |
| `contract/file_naming.py` | 全文 | 用户可见文件名唯一命名中心：`EXISTING_TEMPLATES`（第 21–34 行，现行生产模板）、`generate_existing()`（第 89–94 行）、面向新方案的 `TEMPLATES`/`generate_name()`（第 101–112、180–198 行，目前**仅测试在用**，生产代码全部走 `generate_existing`）、`KINDS` 类型集（第 97 行）、`parse()`/`legacy_scheme()` 只读识别（第 201–218、237–243 行） |
| `contract/script_contract.py` | `stage_file_name()`（第 414–418 行） | 剧本/设定文档名 → `generate_existing('stage_script')`；固定名 `script_raw.md`、`script.md` |
| `domain/project_naming.py` | `dated_path()`（第 6–15 行） | 目录名 `前缀_YYYYMMDD`，占用加 `_2`/`_3` |
| `domain/storyboard_storage.py` | `canonical_name()`（第 77 行） | 分镜工作稿名 → `generate_existing('storyboard_working')`；别名文件 `文件路径映射.json`（第 11 行） |
| `domain/idea_document_paths.py` | `project_script_filename()`（第 59–63 行） | 项目剧本文件名委托 `stage_file_name()`；provider/model 目录身份用 `_storage_name()` 归一（第 79–159 行） |
| 其余生产方 | 见盘点表 | 各自直接调 `generate_existing()` 或固定字符串 |

要点：**`file_naming.TEMPLATES`/`generate_name()` 已经是「新命名方案」的雏形**（`{prefix}_{index:03d}_{slug}{suffix}`，第 101–112 行），但生产侧没有任何调用（全仓 grep 只有 `tests/test_file_naming*.py` 命中 `generate_name(`），现行全部产物仍由 `generate_existing()` 的 `EXISTING_TEMPLATES` 命名。统一命名设计应当在 `file_naming` 内增设新模板角色，而不是各处再写格式串。

## 5. 设计稿：统一「类型＋provider＋年月日」

### 5.1 建议格式

```
{类型}_{provider}_{YYYYMMDD}_{序号}_{可读名}.{后缀}
```

- **类型**：用 `file_naming.KINDS` 的中文类型词或其短代码（剧本/设定/分镜/资产/音频/视频/清单/报告），与索引 `kind` 字段同源，避免又发明一套词表。推荐中文类型词（与现有 `项目名_文件类型_…` 习惯一致），是否全 ASCII 见第 8 节 Q5。
- **provider**：模型池记录的稳定标识（建议 provider＋model 的归一串，如 `seedream`、`qwen-tts`、`local`、`manual`），**不是**界面显示名；非模型产出（用户导入、固定结构文件）用 `manual`/`local` 或按 Q1 决定省略。provider 片段经 `sanitize_part` 归一（`file_naming.py` 第 145–149 行已有 Windows 非法字符清洗）。
- **年月日**：`YYYYMMDD`，与 `dated_path`/`stage_file_name` 现有日期口径一致（本地日期）。
- **序号**：仅当「类型＋provider＋日期＋可读名」仍冲突时追加 `_2`/`_3`（沿用 `dated_path` 语义）；高频类型（同日多集分镜）建议把集/镜编号放进「可读名」段而不是序号段。
- **可读名**：保留现有内容描述（集数、镜号、资产编号、内容摘要），长度沿用 `sanitize_part(limit=80)` 与 `MAX_NAME=120`（`file_naming.py` 第 131、145–149 行）。
- **分隔符**：统一 `_`（与全部现行模板一致）；不用 `-`，避免与 `idea_attachments` 的 `-2` 序号习惯混淆。
- **后缀**：沿用 `.json/.md/.png/.mp4/.srt/.ass/.txt` 现状。

示例（项目「星河」）：

```
分镜_seedream_20261122_EP001_市集追逐.json
首帧_qwenimage_20261122_EP001_SH001.png
音频_elevenlabs_20261122_旁白_主角台词.mp3
视频_seedance_20261122_SH001.mp4
```

### 5.2 同一天同类型多次生成不重名

- 第一策略：**可读名段天然唯一**（集号/镜号/资产编号/内容摘要不同即不冲突），不加序号。
- 第二策略：同名再生（重跑同一集）→ 追加 `_2`/`_3`（`dated_path` 先例），旧文件不覆盖、由用户或生命周期决定去留。
- 第三策略（高频兜底）：需要秒级区分时用 `YYYYMMDD_HHMMSS`（`storyboard_history` 先例，`storyboard_direct_api.py` 第 223 行）。
- 推荐：日常产物用 `_N` 短序号；自动流水线内部版本（分镜历史、回收批次）保留时间戳，二者不强求同一粒度。

### 5.3 中文保留程度（建议值，最终见 Q5）

- 类型与可读名：**保留中文**（现有全部模板如此，`sanitize_part` 已处理非法字符；Windows 保留名由 `validate()` 拦截，`file_naming.py` 第 152–169 行）。
- provider、日期、序号、集/镜/资产编号：ASCII。
- 即「中文骨架＋ASCII 元数据段」，与现状观感连续、改动最小。

### 5.4 兼容办法（旧名只读不改名，新写入用新规则）

1. **新旧并存识别**：`file_naming` 增加新方案的 `parse_new()`（或扩展 `parse()`/`legacy_scheme()`）：新名按「类型_provider_日期」三段定类型与 provider；旧名走既有 `_LEGACY_SCHEMES`（第 135–142 行）＋内容兜底。目录扫描方（`storyboard_catalog_service`、`file_index`、`storyboard_storage`）本来就按**后缀＋内容结构**认文件而非只按名，天然兼容；按名识别的点逐个加双规则：
   - `tts_api.audio_kind()`：新名前缀映射＋旧 `旁白_/BGM_/音效_/整轨_` 前缀同时认；
   - `asset_generated_import_service` 的 `(CHAR|LOC|PROP)` 正则：新名保留资产编号段即可继续命中，建议把编号放可读名首段；
   - `storyboard_catalog_service.file_order/default_source`：`EP*_分镜.json` glob 需扩到新分镜名模式（或改按内容 `episode_id` 字段排序，根治不依赖名）；
   - `storyboard_paths.is_final_dir`：新定稿目录名需纳入识别；
   - `idea_attachments._ARCHIVE_NAME`：附件名若改规则，**必须同步改反解或迁移存元数据**，否则归档读取全废——此类「名即数据」的类型建议第一批就定格式或干脆不改；
   - `file_index` 忽略名单与 `file_naming.parse`：新名模式登记进 `legacy_scheme` 对应的新方案表。
2. **固定名清单/台账不改名**（见 Q6）：它们是契约名，读取方是硬编码；统一命名只作用于「有展示/检索价值的产物文件」。
3. **数据内嵌路径**：`shot['frame']`、`shot['video']`、manifest 内 `file`/`path` 字段、别名表键——这些存的是相对路径，新文件写新路径即可；旧 JSON 里的旧路径继续有效（文件不改名）。新旧 JSON 并存时各自路径自洽，不需要统一改写。
4. **回收站/历史版本**：只按现有规则移动/归档，不追溯改名；`恢复位置.json` 记的是当时路径，天然兼容。

### 5.5 分期建议

| 批次 | 类型 | 理由 |
| --- | --- | --- |
| 第一批（可先行） | 字幕导出（`对白_*`）、交接包导出（`handoff_media`/`handoff_bundle`）、Animatic 媒体名（`animatic_shot`/`animatic_audio`/`temporary_audio`）、音频导入（`audio_import`） | 产物名主要被本阶段 manifest/清单引用，无跨阶段硬编码；`audio_kind` 反解点单一易改 |

## 6. 待用户裁决（每题：推荐＋改选条件）

**Q1 provider 要不要进文件名？**
推荐：**进，但只进「可换 provider 重生成」的产物**（分镜、首帧、视频、音频、资产图）；清单/台账/固定契约名不进。
改选条件：若用户实际很少换 provider、或 provider 标识不稳定（模型池频繁改名），则 provider 段改为可选——新写入仍带，读取方容忍缺段；若用户要求文件名绝对简洁，则全部省略 provider、只在 manifest/台账里记。

**Q2 已有项目里的旧文件要不要提供一次性改名？**
推荐：**不改名**。旧名只读兼容（`legacy_scheme`/`_LEGACY_SCHEMES` 机制现成），新写入用新规则；同目录新旧并存由读取方双认。
改选条件：若用户明确要求「老项目也要统一外观」，则需单独立项做迁移工具（同步改 JSON 内嵌路径、别名表、file_index 重建、回收站清单），风险与工作量都不小，不建议并入本规则。

**Q3 「provider」字段到底取什么？**
推荐：**模型池记录的稳定机器标识**（provider＋model 归一串），非界面显示名；无模型参与的产物用 `manual`/`local`。
改选条件：若模型池记录没有稳定 id（只有显示名会改），则退而求其次用「provider 厂商名」一级粒度（如 `seedream`/`qwen`/`comfyui`），模型级差异留给 manifest 元数据。

**Q4 同一天同类型多次生成的冲突/版本策略？**
推荐：可读名唯一优先；真冲突追加 `_2`/`_3`（`dated_path` 先例）；需要秒级区分的流水线历史保留 `YYYYMMDD_HHMMSS`。
改选条件：若用户希望「重跑即覆盖旧版、旧版自动进历史目录」（类分镜历史模式），则需给每类定义历史去向，复杂度上升；若接受多版本平铺，`_N` 即可。

**Q5 中文保留到什么程度？**
推荐：类型与可读名保留中文（现状连续、`sanitize_part`/`validate` 现成）；provider/日期/编号 ASCII。
改选条件：若目标是跨平台/URL 友好或全 ASCII，则类型段改用 `file_naming.KINDS` 的代码化短名（需新增映射表），可读名可选保留中文或转拼音——后者损失可读性，不建议。

**Q6 清单/索引/台账类固定名是否跟随新规则？**
推荐：**不跟随**。`episode.json`、`assets.json`、五件套 manifest、`index.json`、`产物来源关系.json`、各 `*_状态.json`/台账、`MASTER.mp4` 等是契约名，读取方是硬编码与核验逻辑；统一命名只覆盖「面向人的产物文件」。
改选条件：若用户坚持「任何文件」字面覆盖全部输出，则需把固定名也纳入并给每类配版本化/多名读取，工作量与回归面显著变大，建议单独评估。

**Q7（补充）分隔符与「类型」词表是否认可？**
推荐：分隔符 `_`；类型词表直接复用 `file_naming.KINDS`（剧本/设定/分镜/资产/音频/视频/清单/报告/日志/其他），不另造。
改选条件：若用户想要更细的类型（如「对白」「音效」「BGM」分列），则扩 `KINDS` 或在 provider 段前加子类型段，需同步 `kind_from_suffix`/`file_index.kind_of`。
