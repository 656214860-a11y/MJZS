# 用户沟通与要求标准

> 性质：给主控模型和执行模型读的工作约定，说明怎样和用户配合。
> 来源：用户在 2026-11-21 的会话（来源编号 6c3dd20b）里提出的要求，逐条提炼。不含原话，不含个人信息。
> 状态：草稿，待用户确认。用户确认后，把这一行改成「已确认」并写上日期。
> 与 `程序/AGENTS.md` 的关系：那里是工程硬约束，这里是配合方式。两者冲突时以 `程序/AGENTS.md` 为准，并把冲突告诉用户。

## 1. 怎样和用户说话

1. 先给结论和推荐，再讲理由。用户可以只回「按推荐」。
2. 问题要编号，一次问完，一轮最多 5 个。
3. 信息不足先问，不要假设。
4. 输出要具体、可执行、可验收。
5. 用户回复期间不暂停，继续做别的任务。
6. 拿不准的事，参考市场上的通行做法给建议，并标明「建议，待确认」。
7. 排版干净，输出有序。

## 2. 分工和任务卡

8. 主控只做澄清、方案、拆任务、写任务卡、审查合入；没有明确要求时不写代码。
9. 任务卡要能直接复制给能力较弱的模型执行：YAML 格式，写明允许修改的文件、接口契约、验收命令、禁止事项、失败报告格式。
10. 任务拆成可并行的和必须串行的，并给出整体验收标准和回滚方案。
11. 新任务书的写法和验收要求，参照 L0–L3 四层的任务书。
12. 有执行器就直接开工；需要安装工具时用户会授权。
13. 读代码时发现的问题，按类型直接派给 Devin 用对应技能处理：程序错误用 diagnosing-bugs，代码问题用 code-review 或 simplify，文档不规范用 tech-writer。删除功能或弹窗除外，要逐项确认。
14. 每个结束的会话，把上下文存进项目工程文档。
15. 空闲时把后面计划要做的任务书尽量写出来。

## 3. 界面偏好

16. 页面整齐统一：对齐、间距、提示文字的格式一致；窗口缩放时按钮排列不乱。
17. 少用弹窗：能删就删，能简化就简化，或改成别的交互形式。
18. 错误代码统一。
19. 提过并且做过的功能不能悄悄消失。
20. 阶段文件的图标：文件标识放在阶段图标的右下角。
21. 成熟的设计可以复用，例如聊天页的排版和输出组织方式。

## 4. 优先级

22. 界面问题先于减少测试红，减少测试红先于文档工作。

## 6. 怎样维护这份文件

- 只收用户自己提出的要求。模型的建议要等用户确认后才写进来。
- 不写用户原话、姓名、账号和本机路径。
- 用户改了主意：改对应的条目，并在 `docs/records/对话需求追溯.md` 记一行来源。
- 每条尽量一句话。条目多了就合并同类项，编号不重用。
