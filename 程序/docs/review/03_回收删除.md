# 03 用户可见删除（`storage_maintenance.recycle_paths`）

规则：用户能看见的删除，一律移进回收站，不做物理删除（AGENTS §2.3 第 14 条）。主链路是“先写计划，再逐项移动”。越界、链接、`..` 都有校验，行为基本可靠。

## 时序：删除（以删首帧为例）
1. 界面先确认：`desktop_media_pages.py:450-462` → `stage_execution_service.py:1086 delete_stage_keyframe`。
2. 服务层再校验：只允许删 frames 目录下、没有被共用的文件（`keyframe_lifecycle_service.py:30-38`），然后调 `recycle_paths(base, ...)`（`:42`）。这里的 base 是剧集目录，不是项目根。
3. 建批次目录：`<root>/工作流任务/回收站/自动维护_<秒>_<uuid8>`（`storage_maintenance.py:59-61,109-112`）。
4. 逐项规划 `plan_recycle`（`:122-132`）。是链接或连接点、在 root 外、不存在、目标已被占用的项，静默剔除；全部被剔除时返回 `[]`，由调用方报错。
5. 原子写入清单 `恢复位置.json`，状态 planned（`:184-185`）。
6. 逐项 `shutil.move`（`:141`），每移完一项重写一次清单（`:190`）。
7. 全部成功后，清单标为 committed（`:199`），并调用 `file_cache.recycled`，让原位置和回收站位置的缓存都失效（`:200`）。
8. 之后如果发布 `episode.json` 失败，用 `restore_latest_recycled_path` 撤销这次删除（`keyframe_lifecycle_service.py:51`）。

## 时序：恢复
1. 入口有三类：
   - 首帧／资产：`restore_latest_recycled_child`／`_path`（`:304,328`）；
   - 通用恢复页：`recycle_recovery_controller.py` → `recycle_recovery_service.py:11-23`；
   - 分镜：`storyboard_recycle_service.py:146-153`。
2. 选最新一批：按目录名倒序，跳过 rolled_back（`:314-324`）。
3. `restore_recycle_batch` 校验（`:210-251`）：
   - 批次目录必须在回收站内；
   - `_restore_location` 拒绝 `..`、等于 root、越出 root、任一级祖先是链接（`:821-831`）；
   - 目标已存在、条目重复、条目互相嵌套，都是一项不动，直接报 ValueError。
4. 逐项 `rename`；某项失败就反向回滚，报“恢复未完成，已回滚”（`:255-267`）。
5. 成功后调用 `file_cache.recycled`。清单不改写，这是设计如此。

## 失败模式

| 场景 | 现在会怎样 | 证据 | 测试 |
| --- | --- | --- | --- |
| 路径在项目外、是链接、带 `..` | 删除时静默剔除，恢复时报错 | `:126`；`:242,824` | `test_recycle_directories.py`、`test_recycle_recovery_service.py` |
| 一批中途失败 | 已移动的项撤回（目标被占用的不覆盖），清单写 rolled_back，原异常重新抛出 | `:192-198,147-167` | `test_recycle_write_ahead.py` |
| 移动途中进程被杀 | 清单逐项落盘；回滚或恢复时按“文件是否真在回收站里”逐项处理 | `:272-301` | `test_recycle_write_ahead.py` |
| 恢复时原位置已被占用 | 一项不动，报错；分镜和首帧另有前置检查 | `:244-245`；`keyframe_lifecycle_service.py:76-77` | `test_recycle_restore.py`、`test_project_recovery.py` |
| **文件被别的进程占用（Windows）**（推断） | `os.rename` 失败后，`shutil.move` 退回为“先复制，再删源”。单个文件：回收站多出一份副本，原文件还在，该项标 failed、不撤回，之后恢复会因原位置被占而拒绝。**目录：`rmtree(src)` 中途失败，源目录被删掉一半**，完整副本只在回收站里 | `:141`（`shutil.move`） | 无测试 |
| 移动成功、写清单失败（推断） | 该项被改标为 failed，但文件其实已在回收站；`_undo_moves` 只撤回 moved／planned，所以这一项不会被撤回，只能事后手动恢复 | `:190,193` | 无测试 |
| 要删的路径就是 root（推断） | 能通过规划，随后 `shutil.move` 因“目录移进自身”失败，整批回滚；批次目录和 rolled_back 清单留在回收站 | `:126-141` | 无测试 |
| 要删的路径在回收站里 | `plan_recycle` 不排除回收站，会把旧批次嵌套搬进新批次 | `:122-132` | 无测试 |
| 先恢复一批，再“恢复最新” | 命中刚恢复过的那批（清单没改），报错，不会退回到更早一批 | `:323-324,244` | — |
| 回收站越来越大 | 没有任何清空或过期清理入口，回收站只增不减；清理和扫描都跳过回收站 | `:768,781,800` | — |

## 绕过 `recycle_paths` 的地方
- **第二套回收实现**：`storyboard_recycle_service.recycle_files`（`:76-124`），入口是 `storyboard_files.py:162` 和 `storyboard_page_controller.py:114`。
  - 自己拼批次目录，清单是旧格式（没有 state 字段）；
  - 用 `rename` 移动；
  - 回滚的 `rename`（`:106`）没有 try，一旦失败就盖掉原始异常，剩下的项不再回滚；
  - 不调用 `file_cache.recycled`。
- **回收站分散在多个 root 下**：首帧在剧集目录、资产在资产 base、技能导入在程序目录、项目删除在项目库根目录。通用恢复页只汇总“项目内”和“项目库”两处，其余位置在恢复页里看不到（首帧和资产页自己的恢复按钮仍可用）。
- 直接物理删除只出现在临时文件、缓存、日志、回滚和空目录上，没有发现删除用户成果的情况。
- **门禁的盲区**：`test_deletion_gateway`／`test_remove_authority` 只拦 `os.remove／unlink／rmdir／removedirs` 和 `shutil.rmtree`；`test_recycle_service` 额外拦 `.unlink`，但不递归扫子目录。拦不住的有：`Path.rmdir`、用 `rename`／`shutil.move` 搬走、`from shutil import rmtree` 别名导入。也没有门禁要求用户可见删除必须调用 `recycle_paths`，分镜那套实现就是这样漏掉的。

## 建议跟进
1. `_move_record` 用 `os.rename`（同盘）代替 `shutil.move`。rename 失败就整项失败，不退回为“复制＋删源”，避免删掉半个目录。这一条优先级最高，需要先写一个模拟占用的复现测试。
2. `storyboard_recycle_service.recycle_files` 改为委托 `recycle_paths`，旧格式清单保留只读兼容。
3. `plan_recycle` 排除回收站自身和 root 本身。
4. 回收站清理策略（比如按天数）由你拍板要不要做。
