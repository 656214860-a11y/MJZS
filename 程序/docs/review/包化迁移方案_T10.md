# T10 顶层模块包化迁移方案（先出方案，经用户批准后按搬家轮执行）

## 现状

- `程序/` 顶层 359 个 `.py`（不含测试），全部平铺；`tests/architecture/_layers.py` 登记分层，`PROJECT_MAP.md` 手工导航。
- 前缀族已天然聚类（见下表），但族内仍有跨层混合（如 `asset_*` 横跨 L1–L4）。

## 目标包结构（按层为主、前缀族为辅）

```
程序/
  contract/      # 现 L0：pet_bus, *_contract, service_contract, error_codes, artifact_schema, stage_layout, storyboard_paths, project_context …
  infra/         # 现 L1：file_cache, model_pool, model_secrets, app_logging, storage_maintenance, platform_tools, api_endpoints …
  domain/        # 现 L2：writing_*, asset_*, keyframe_*, storyboard_*, delivery_* …（后续按族再分子包）
  orchestrator/  # 现 L3：stage_*, skill_orchestrator, agent_dispatch, writing_api …
  ui/            # 现 L4：desktop_*, pet_ui_*, ui_*, app.py, skill_panel_* …
```

## 迁移规则（每轮一个前缀族，测试搬家轮 §3.6 口径）

1. 只 `git mv` + 改 import；测试逻辑、断言、fixture 原样。
2. 旧路径留薄转发（`from pkg.mod import *` 并登记 `test_legacy_facade_manifest`），下一阶段清除。
3. 同轮更新：`_layers.py`、`PROJECT_MAP.md`、`distribution_manifest.md`、动态导入字符串（`ui_plugin_registry`、`stage_handler_registry`）、`sys.path` 假设、`.gitignore`/打包清单。
4. 每轮验收：`test_layers`、`test_no_circular_import`、`test_static_hygiene`、`test_startup_budget` 绿 + `distribution_build.py --verify`。

## 建议顺序（风险从低到高）

| 批次 | 前缀族 | 规模 | 风险 |
| --- | --- | --- | --- |
| 1 | `account_*`、`project_*` | ~15 文件 | 低，偏 L1/L2 |
| 2 | `error_codes` 等已建小模块并入 `contract/` | 5–10 | 低 |
| 3 | `writing_*` | ~15 | 中，L2/L3 混合 |
| 4 | `asset_*`/`asset_batch_*`/`asset_reference_*` | ~25 | 中，族内跨层需先标层 |
| 5 | `keyframe_*`、`storyboard_*` | ~20 | 中高 |
| 6 | `desktop_*`/`pet_ui_*`/`ui_*` | ~50 | 高，UI 动态装配多 |
| 7 | `app.py`/`pet_*.py` 拆分 | 10+ | 最后，单独立项 |

## 前置工作（下一轮先做）

1. 写一个只读 AST 扫描器：输出每个顶层模块的「实际 import 依赖层」与「被谁 import」，生成族内跨层清单——跨层族先拆纯函数部分再搬。
2. 用户确认包名（`contract/infra/domain/orchestrator/ui` 还是中文无关的短名）与是否允许 `__init__.py` 再导出。

## 扫描实测（2026-11-15，`scripts/package_dep_scan.py`）

工具已落地：`程序/scripts/package_dep_scan.py`（只读 AST，复用 `tests/architecture/_scan.py` 的口径；`--json` 全量、`--family <前缀>` 单族）。口径：顶层生产模块 362 个（不含自检器与 `test*`），层级分布 L0=30／L1=50／L2=71／L3=75／L4=130／L5=2；未登记的 4 个是 `TOOLS` 表内外围脚本（`batch_frames_tool` 为目录包，不在顶层）。

**结论一：几乎所有前缀族都是跨层的**，38 个族里 36 个横跨 ≥2 个 L 层（`asset`/`pet`/`project`/`script`/`stage`/`workflow` 甚至横跨全部 5 层）。「按层分包、按族分批搬」的原方案成立；不存在「整族同层、可整包直搬」的捷径。

**结论二：批次顺序按任务书「先 L0、后 UI」修订**（原表批次 1 的 account/project 族实际横跨 L1–L4，且 `project_context`/`project_stages` 是被引 28/33 处的 L0 契约，风险高于小体量 L0）。修订后：

| 批次 | 内容 | 规模 | 说明 |
| --- | --- | --- | --- |
| 1 | `contract/` 试点：小体量 L0 模块 | ~10 | `error_codes`（产入 1）、`model_protocol`（1）、`pet_settings_contract`（3）、`script_brief`（1）、`script_output_spec`（1）、`storyboard_contract`（1）、`shot_selection`（2）、`frame_checks`（2）、`api_models`（4）、`artifact_lineage`（3）——先跑通包目录、`__init__`、薄门面、登记表与分发清单全链路 |
| 2 | `contract/` 其余 L0 | ~20 | `pet_bus`（59）、`platform_tools`（60）、`stage_layout`（40）、`project_stages`（33）、`script_contract`（32）、`stage_path_service`（30）、`storyboard_paths`（31）、`project_context`（28）、`service_contract`（32）等，引用面大但同属一包 |
| 3 | `infra/`（现 L1） | ~50 | 按族分 2–3 轮 |
| 4 | `domain/`（现 L2） | ~71 | 按族分 3–4 轮；`account_*`/`project_*` 业务面在此批 |
| 5 | `orchestrator/`（现 L3） | ~75 | 按族分 3–4 轮 |
| 6 | `ui/`（现 L4） | ~130 | 按族分 4–5 轮；`desktop_*`/`pet_ui_*`/`ui_*` 动态装配最多，放最后 |
| 7 | `app.py`/`pet_*.py` 拆分 | — | 单独立项，不占包化轮次 |

**结论三：每轮搬家必须同轮更新的触点**（扫描＋门禁源码核对）：

- `tests/architecture/_layers.py`：`LAYERS` 登记包名（`contract`→0 等）与留存模块名；`tests/architecture/_scan.py` 的 `production_files()` 只扫顶层 `*.py`，包内模块须纳入递归口径或等价登记，否则搬走的模块会逃出分层/环依赖门禁（`agent/` 子包目前就是这种盲区）。
- `distribution_manifest.md`：`程序/*.py` 通配不含 `程序/<包>/*.py`，每建一个包目录须在「必须保留」表加 `程序/<包>/**`，否则 `distribution_build.py --plan` 归为 undecided、`--build` 拒绝。
- `PROJECT_MAP.md`、`architecture.md` §3 分层表与权威源表、`AGENTS.md`（16 KB 上限内替换式更新）。
- 动态导入字符串：`ui_plugin_registry.UI_PLUGINS`、`stage_handler_registry`、各 `import_module('...')` 常量实参——扫描确认被搬模块在批次 1 候选集中无动态引用，但每批仍须重跑 `--json` 核对。
- `smoke_test.py` 的 `import`/`route`/`widget` 检查项用扁平模块名——薄门面保留期间无需改；`_AFFECTED_TEST_ALIASES` 同理。
- `h3_launcher.pyw`、`启动漫剧制作助手.pyw`：`sys.path` 已含 `程序/`，包可直接解析；入口 `from desktop import Desktop` 由门面兜底。
- 测试侧：批次 1 候选模块的测试引用面合计约 110 个文件（`project_stages` 38、`project_context_factory` 13、`entitlement_service` 10、`desktop_project_pages` 7…）。薄门面使测试 import 原样可用，符合 §2.3 第 16 条「只修 import、不动断言」的最小口径；是否同步把测试 import 改写为包路径，列入待确认项。

**薄门面的额外理由**：并行车道上未合入的分支仍按扁平名 import；门面让它们 rebase 后不立即断。门面文件本身是顶层 `*.py`，会继续被 `production_files()` 扫描并在 `LAYERS` 中保留原名登记（`test_registered_names_resolve…` 要求登记名能解析到 `<名>.py` 或 `<名>/__init__.py`，门面正好满足前者）。

## 已确认口径（2026-11-15 用户拍板）

1. **包名**：`contract/`（L0）、`infra/`（L1）、`domain/`（L2）、`orchestrator/`（L3）、`ui/`（L4），即上文目标结构。
2. **`__init__.py`**：只放 docstring，不做再导出；消费方一律 `import <包>.<模块>`／`from <包>.<模块> import 名`，避免 `__init__` 顶层 import 引发的循环导入。
3. **批次 1**：`contract/` 试点小模块（上表批次 1 的 ~10 个小体量 L0），先跑通全链路。
4. **测试 import**：不改写，继续按扁平名命中薄门面；生产侧 import 每轮改写为包路径。测试侧是否统一改写留到门面清除轮再定。
