# 01 阶段启动 → 引擎子进程 → 产物发布

**先看这一条**：大多数阶段从 `stage_handler_registry.start()` 出发后，**不会**进入 `workflow_engines._run`。它们会打开一个交互式 CLI 窗口，程序不等这个窗口退出。在生产代码里，后台调用 `run_background` → `_run`、并等子进程结束的，只有白模批次一处（`previs_automation.py:154`）。所以这条路径其实分成两条：交互路径和后台路径。

## 时序

**入口（UI 线程）**
1. `desktop_pet_bridge.py:68 pet_start` 调用 `stage_handler_registry.py:107 start()`。
2. 先查制作锁（`:109`），再按阶段分流：
   - storyboard 走 `:114`；
   - script_structure／delivery 经 `stage_exec.py:32/83` 由 skill_orchestrator 执行，成果用 `publish_stage_text` 发布（`stage_exec.py:74`），这条不起引擎；
   - 其余阶段走 `desktop_pet_bridge.py:69 _start_unattended_stage`。

**交互路径**
3. `desktop_idea_chat.py:868 open_flow_agent` → `:889 build()`。`host.worker` 为真时拒绝重复发送（`:896`）。
4. 后台线程 `prepare`（`:927`）里调 `agent_dispatch.claim`（`agent_dispatch.py:27`），持 `task_lock` 按签名去重。
5. UI 线程 `dispatch`（`:988`）→ `launch_cli`（`:1009`）申请阶段槽位。槽满就排队：每 200 ms 轮询一次，最多等 120 秒（`:1077-1102`）。
6. `workflow_engines.py:296 launch_interactive` → `:371 launch_windows_app` 开一个新控制台窗口，`:389-390` 把槽位绑到进程上并登记进程。到这里交互路径就结束了。
7. 完成不看进程退出，看产物：`pet_ui_stages.py:35 _complete_if_verified` → `stage_completion_service.emit_verified_completion`（见第 02 页）。

**后台路径（白模）**
8. `desktop_auto_flows.py:523` → `previs_automation.py:78 start` 起一个线程。外层还有 `desktop_automation_service.py:392 run`：它另起一个 work 线程，监管线程每 20 ms 做一次 checkpoint（`:412-423`）。
9. 每个镜头调一次 `workflow_engines.py:234 run_background`：先预留槽位，满了直接抛错，不排队（`:236`、`workflow_process_registry.py:41`）；再按引擎分流到 client-cli／qwen（`qwen_adapter.py:121`）／opencode／codex·claude。
10. `_run`（`:155`）：Popen → `register_process`（`:160`）→ `platform_tools.communicate_or_kill`（`:179`，超时就 taskkill /T 结束整棵进程树）→ `finally` 里 `forget_process`（`:168`）。默认超时 2 小时，阶段配置的 `timeout_seconds` 可以改（R1853）。
11. 写报告分两种：
    - Codex 由 CLI 自己用 `-o` 直接写（`:109`）；
    - Claude／qwen／opencode 先写临时文件，再 `agent.core.replace` 转正，最后 `save_text`（fsync 后原子替换，`agent/core.py:79`）。
    这些写入都不在事务里。
12. 完成回报：worker 调 `announce`（`previs_automation.py:47`）把结果放进 `state['news']`；UI 心跳（`desktop_auto_flows.py:211-216`）取出后交给 `pet_report`。

**事务发布（两条路径共用）**
13. `stage_publication.py:23/55/82 publish_stage_*` 都包在 `agent/publication.py:148 transaction()` 里：
    - 每个目标先备份，再写 journal（`:128-144`）；
    - 提交时 journal 标为 committed（`:167`）；
    - 出异常当场回滚（`:171`）。
14. 启动恢复有两处：
    - 打开项目时调 `recover_stage_publications`（`desktop.py:834`）；
    - 每次 `access()` 也会扫一遍，把 pending 的 journal 回滚（`publication.py:118-120`）。

## 失败模式

| 场景 | 现在会怎样 | 证据 | 测试 |
| --- | --- | --- | --- |
| 后台 CLI 卡住 | 2 小时后结束整棵进程树，并报明确错误 | `workflow_engines.py:161-163`；`qwen_adapter.py:141-143` | `test_latent_defects_r1853.py` |
| **监管期限比引擎超时短**（推断） | 外层 `ExecutionControl` 默认 3600 秒（`desktop_automation_service.py:439`），只在 checkpoint 时生效；`_run` 没用剩余时间去收短自己的超时。监管线程抛 `ExecutionStopped` 之后，子进程照样跑，仍占着槽位，最多再跑 1 小时 | `desktop_automation_service.py:413-423` | 无测试 |
| **普通取消不杀进程** | `cancel` 只给 control 置停止标记；只有“强制停止”才走 `workflow_engines.terminate` 结束已登记的进程 | `desktop_automation_service.py:484`；`workflow_engines.py:125-143` | 强制停止有：`test_opencode_engine.py`、`test_workflow_engines_run.py` |
| CLI 非零退出 | codex／claude 抛“执行失败”；claude 的临时响应在 `finally` 里被删掉，不留诊断（client-cli／opencode 会保留）。白模把该镜记为 failed，继续做下一镜 | `workflow_engines.py:230-231,270`；`previs_automation.py:164-169` | `test_force_quit.py`、`test_run_background_equivalence.py` |
| 报告为空 | claude／qwen／opencode／client-cli 报“未返回制作报告正文”。**codex 不查空报告**，只靠后面的视频 `verify` | `workflow_engines.py:226`；`previs_automation.py:157` | codex 空报告无测试 |
| 写盘时磁盘满或没权限 | 删掉临时文件，旧的正式文件保留；`PermissionError` 重试 5 次、每次间隔 50 ms；事务内失败整包回滚 | `agent/core.py:52-62,94-97`；`publication.py:169-171` | `test_publication_recovery.py`；磁盘满（ENOSPC）无测试 |
| 发布到一半进程被杀 | 下次 access 或打开项目时按 journal 回滚：已有文件从备份恢复，新建的文件删掉。journal 本身坏了就拒绝读取（RuntimeError） | `publication.py:65-84` | `test_publication_recovery.py`（逐索引注入死亡）、`test_publication_transaction.py` |
| 引擎报告、白模 `状态.json` 写到一半 | 不在 journal 管辖内，只靠原子替换保证不出半份文件 | 同第 11 步 | — |
| 同一阶段连点两次 | 交互路径有三道防线：worker 标记、签名去重、槽位上限。后台路径槽满直接拒绝；白模的 `state['busy']` 判断没加锁，未核实是否只在 UI 线程调用 | `desktop_idea_chat.py:896`；`agent_dispatch.py:27`；`previs_automation.py:79` | `test_workflow_process_registry.py` |
| **槽位跨项目共享** | 槽位键只用阶段名，不含项目，同一阶段的并发上限由所有项目一起分 | `workflow_process_registry.py:33-44` | — |
| 正常关闭时还有子进程 | 确认后 `force_quit` 停掉白模批次与自动化进程；`finish_close` 再兜底结束一次，交互窗口也一起结束 | `desktop.py:742-801` | `test_force_quit.py`、`test_exit_maintenance.py` |
| 程序被直接杀掉 | 没看到 job object 之类的机制，子进程可能残留（推断） | — | 无测试 |

## 建议跟进
1. `_run` 的超时取 `min(引擎超时, control.remaining())`；`ExecutionStopped` 时结束已登记的进程。
2. codex 路径补空报告检查，与其他引擎一致。
3. claude 非零退出时保留临时响应，供诊断。
4. 确认阶段槽位跨项目共享是不是有意的；如果不是，键里加上规范化后的项目路径。
