# 04 三虎跨重启续跑台账

**先看这一条**：没有统一的“阶段续跑台账”，落盘的只有下面三份文件。重启后阶段状态会读回来，但三虎每次开机都会被强制设成只提醒档、手动模式（`pet_ui.py:874` → `pet_ui_stages.py:711-729`）。所以重启后**不会自动重新派发** `stage_handler_registry.start()`，要等用户自己切到半自动或全自动。

| 文件 | 路径 | 内容 |
| --- | --- | --- |
| 阶段状态 | `<项目>/工作流任务/宠物/阶段状态.json`（`pet_state.py:16`） | `stages{stage:{state,reason,attempts,detail}}`、耗时、单位 |
| 资产批次台账 | `<项目>/workflows/资产批量记录.json`（`asset_batch_state_service.py:22`） | 每个资产一条：`submitting/queued/imported/failed`，以及 prompt、url、references、record |
| 资产退避台账 | `<项目>/workflows/资产续跑台账.json`（`asset_resume.py:28,44`） | 每个资产一条：attempts、`waiting/stopped`、`next_try`（墙钟） |

三份都是临时文件加 `os.replace` 原子写。

## 时序
1. **派发**：`tune_advance` → `auto_stage` → `start_stage` → `desktop.pet_start` → `stage_handler_registry.start(trigger='auto')`（`pet_ui_stages.py:139-146,285`）。派发前**不写**阶段状态。
2. **阶段状态由事件驱动**：收到 `stage.started/completed/failed/retrying` 后，`Machine.apply` 发现状态有变化才保存（`pet_state.py:80-101`）。中途进度不单独落盘。
3. **资产台账先写再提交**：
   - 提交前标 `submitting`（`asset_batch_execution.py:150`）；
   - `comfy_service.submit_graph` 先写 `workflows/comfy_*.json`（带 client_id），再 POST，拿到 prompt_id 后改成 queued（`comfy_service.py:163-173`）；
   - 批次台账随后改成 queued（`:153`），导入完成后改成 imported（`:157`）。
4. **退避台账**：每轮补资产结束后，如果还缺图，次数加一，`next_try = now + 60 × 次数`，到上限标 stopped（`asset_resume.py:89-113`）；缺图补齐后清掉。
5. **进程被杀**：没有退出时的收尾写入。
6. **重启**：
   - 打开项目时 `Machine.load()`。原来是 running 的阶段仍是 running，只是计时重新开始（`pet_state.py:235-239`）；
   - 退避台账换算成 monotonic 的到期时间（`desktop_asset_pages.py:84-99`）。
7. **续跑判定**：
   - 开机档位被压回只提醒，`advance()` 返回 None；
   - 即使档位允许，只要阶段状态里还留着 running，`busy()` 就为真，`tune_advance` 直接返回（`pet_ui_voice.py:470-479`；`pet_ui_stages.py:137`）；
   - 资产自动轮询要求 `mode=='auto'`，开机是 manual，所以退避台账到期也不会触发。
8. **用户切到半自动或全自动**：`Auto.arm_from(states)` 跳过 success／skipped，从第一个没完成的阶段接手，包括残留的 running（`stage_flow.py:379-393`）。`set_mode('auto')` 会立即派发一次。资产批次重跑时，`resume_record` 接上已确认的旧任务（`asset_batch_execution.py:71-83`）。

## 失败模式

| 场景 | 现在会怎样 | 证据 | 测试 |
| --- | --- | --- | --- |
| 资产已提交、台账还没写 queued 时崩溃 | 台账停在 submitting。重启后判为“不确定”，**不重新提交**，并提示用户去核实；核实后用 `release_uncertain` 放行 | `asset_batch_state_service.py:61-66`；`asset_batch_execution.py:81-82` | `test_assets.py` `test_batch_keeps_uncertain_and_never_resubmits` 等 3 条 |
| 阶段 started 事件发出前崩溃 | 阶段状态里没有记录，仍是 pending，以后会重新派发；后台任务有没有留下半成品未核实 | `pet_state.py:80-101` | — |
| 阶段状态或退避台账 JSON 损坏 | 当作没有记录：阶段全部回到 pending，退避台账当作空 | `pet_state.py:211-214`；`asset_resume.py:54-57` | `test_corrupt_snapshot_falls_back_to_defaults`、`test_a_broken_ledger_counts_as_no_ledger` |
| **资产批次台账 JSON 损坏** | 返回 `{}`，submitting 记录跟着丢失，可能重复提交、重复扣费（推断） | `asset_batch_state_service.py:28-29` | 无测试 |
| **状态写着 running，但进程已经没了** | 没有 pid，也没有心跳，不判断是否过期。running 原样恢复，`busy()` 一直为真，自动推进每一拍都跳过，处于卡住状态；只有用户手动切到全自动、`set_mode` 立即派发时才会绕过。按钮上的“执行中”只存在内存里，重启后不显示 | `pet_state.py:235-239`；`pet_ui_stages.py:137`；`stage_flow.py:55` | 只测了“计时重新开始”；卡住无测试 |
| 上游改了以后续跑（阶段层） | success 状态不带上游指纹，`arm_from` 直接跳过；门禁只查文件在不在 | `stage_flow.py:388-391` | — |
| 上游改了以后续跑（资产层） | `resume_record` 比对 prompt／url／references／generation，不一致就报冲突并跳过 | `asset_batch_execution.py:73-76` | `test_resume_record_rejects_changed_resume_identity` |
| 两个窗口同时开同一个项目 | 没有单实例锁，也没有台账文件锁，三份文件后写的覆盖先写的。进程内用 `Auto.active` 和 `keep_active` 防重复，跨进程不防 | `stage_flow.py:400`；`pet_ui_stages.py:782-785` | 无测试 |
| 崩溃前用户按了暂停 | 暂停标记只在内存里。`pause(stage=…)` 会发 `stage.failed` 写进阶段状态；重启后该阶段是 failed，切到自动档时从这里接着跑，不再暂停 | `pet_agent.py:838,897-902`；`stage_flow.py:359` | — |
| **项目移动或改名后，资产处于 queued** | 资产台账的 `record` 是绝对路径，移动后找不到：submitting 的判为不确定并跳过；queued 的 `resume_record` 返回 None，**会重新提交，可能重复扣费**（推断） | `comfy_service.py:163`；`asset_batch_execution.py:73-83` | 无测试 |
| 系统时钟往回拨 | 退避台账用墙钟：等待时间会变成“拨回的时长＋原等待”，往前拨则立刻重试，没有夹紧。进程内换算成 monotonic 后不受影响 | `asset_resume.py:116-122` | 无测试 |

## 建议跟进
1. 资产台账里的 `record` 改存相对路径（读取时兼容旧的绝对路径）；`_resumable_record` 读不到 queued 任务时按“不确定”处理，不要重新提交。这两条都涉及重复扣费，优先级最高。
2. 资产批次台账解析失败时，不要当作空台账，应该阻止本次批量提交并提示用户。
3. 打开项目时，残留的 running 阶段改为 interrupted（或 failed 并注明“上次退出时未完成”），避免自动推进卡住。
4. 是否加单实例锁（同一项目只允许一个窗口打开），由你拍板。
