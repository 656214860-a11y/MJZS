# 03 安装、签名与分发

本册覆盖目标格式、签名证书与保管、企业部署通道、更新包完整性校验。**现状是「随附解释器 + 目录副本」，没有任何安装器**；SBOM 与发布供应链门已经实现，安装器和真实签名仍待实现。

## 1. 现状盘点

| 项 | 现状 | 证据 |
|---|---|---|
| 安装器配置 | **不存在**（无 `.iss`／`.wxs`／`.nsi`／`.msix`／`.spec`） | 全仓扫描 0 命中 |
| 分发形态 | 目录副本 + 脚本 | `scripts/distribution_build.py`（`--plan/--build/--verify`） |
| 分发清单 | 已有白名单机制 | [`distribution_manifest.md`](../../distribution_manifest.md)（构建器消费） |
| 完整性 | **已有逐文件 sha256** | `distribution_build.py` 写 `分发清单.json`；`verify()` 比对 mismatch/extra |
| 签名 | **未实现** | 需要真实构建机密钥；发布门拒绝伪造通过 |
| SBOM | **已实现** | `scripts/sbom.py` 默认接入 `distribution_build.py`；`distribution_selfcheck --release` 校验 |

**关键结论**：完整性校验的**基础已存在**（`分发清单.json` + `verify()`），缺的是「用它」——更新流程不验包。

### 1.1 现行发布闭环（安装器落地前，后续开发必须执行）

Git 推送只更新备份仓库。用户启动的是另一份目录副本。执行步骤以 `docs/process/发布检查单.md` 为准，失败模式以 `docs/review/安装更新与恢复方案_A15.md` 为准。每一轮要交付给正在使用的程序时，按这个顺序做完才算发布，不能停在 `git push`：

1. 主干已合入，本机出口 CI 已通过。
2. `scripts/distribution_build.py` 在新的空目录构建副本，`verify()` 对照 `distribution_manifest.md` 与 `分发清单.json`。
3. 在该副本上冒烟启动，确认程序能打开，且 `config.json`、`projects.json`、`desktop_settings.json`、`private/`、`data/` 与用户项目没有被覆盖。
4. 确认可用后把启动入口切到新目录。旧目录保留一个完整使用周期；启动失败或数据不对就切回旧目录，不在用户数据上做 `git reset`。

安装器和代码签名仍按本册后续章节，未实现前不得把「仓库已推送」写成「用户侧已更新」。操作口径与 `runbook.md` §5、§12 一致。

## 2. 目标安装格式

采用**双通道**：个人用户用 EXE，企业用 MSI。

| 通道 | 技术 | 产物 | 适用 |
|---|---|---|---|
| 个人 | **Inno Setup 6** | 单文件 `漫剧助手-<版本>.exe` | 个人用户、单机安装 |
| 企业 | **WiX Toolset v4** | `漫剧助手-<版本>.msi` | 组策略／SCCM 推送、静默安装 |

### 2.1 为什么双通道

| 格式 | 优点 | 缺点 |
|---|---|---|
| Inno Setup EXE | 单文件、中文向导成熟、免费、压缩率高 | 非企业标准；静默参数弱；组策略不便 |
| WiX MSI | 企业标配；组策略／SCCM 可推；卸载干净；支持 `ADDLOCAL` 特性选择 | WiX XML 冗长；打包数万文件慢 |
| **MSIX** | 现代、容器化、自动更新 | **排除**：容器化模型与「随附完整 Python 解释器」冲突；需重打包 |
| 便携 ZIP | 零安装 | 保留为备用（当前形态） |

### 2.2 安装包内容与目录

安装后目录结构（与当前分发副本一致）：

```
<安装目录>\
├─ 启动漫剧制作助手.pyw        # 入口
├─ 运行环境\Python\            # 随附解释器（约 42 MB，数万文件）
├─ 运行环境\ffmpeg\            # FFmpeg/FFprobe + LICENSE/NOTICE
└─ 程序\                       # 产品代码、资源、SKILL
```

### 2.3 安装器必须处理的项

| 项 | 要求 |
|---|---|
| 升级保留 | **只覆盖程序文件**，保留 `config.json`、`projects.json`、`desktop_settings.json`、`private`、`data` 下的运行数据（内置的 `data/skill_note_terms_zh.json` 是程序文件，随包覆盖）、`配置/宠物`、`配置/素材库.json`、用户项目与素材 |
| 卸载 | 不删用户项目与素材；询问是否保留配置 |
| 权限 | 默认按用户安装（`%LOCALAPPDATA%`），避免 UAC；企业 MSI 支持 `ALLUSERS=1` |
| 静默参数 | MSI：`/qn`；EXE：`/VERYSILENT /SUPPRESSMSGBOXES` |
| 快捷方式 | 桌面 + 开始菜单，图标随包 |
| 首次运行 | 不自动下载任何网络内容 |

### 2.4 升级与回滚

| 项 | 方案 |
|---|---|
| 升级前快照 | `scripts/release_snapshot.py --snapshot` |
| 升级方式 | 覆盖安装（保留用户数据） |
| 回滚 | 保留上一版安装包；回滚靠 Git 与快照 |
| 升级后验证 | 启动自检 + 分发副本自检（`distribution_selfcheck.py`） |

## 3. 签名方案

### 3.1 决策：首期用 GPG／minisign，暂不买代码签名证书

| 方案 | 成本 | 效果 | 裁决 |
|---|---|---|---|
| 不加签，只发 sha256 | 0 | 可验完整性，不解决信任提示 | 不足 |
| **GPG detached 签名** | 0 | 构建机私钥签 `SHA256SUMS`，用户用公钥验证 | **首期采用** |
| **minisign／signify** | 0 | 单文件公钥，验证一行命令 | **首期采用（更顺手）** |
| OV 代码签名证书 | 约 2000–4000 元／年 | 消除「未知发布者」；SmartScreen 声誉需累积 | **暂不买**，触发条件见 3.4 |
| EV 代码签名证书 | 约 5000–9000 元／年 + 硬件 token | 立即获 SmartScreen 信任 | **暂不买** |

**理由**：开发预算 1 万元（[PRD §8](../requirements/产品需求规格.md)），OV 证书一年吃掉 20–40%。证书解决的是**分发信任**，不是**产品正确性**。当前还没有需要装的付费用户。

**如实记录的后果**：未加签的安装包在 Windows 上会触发 SmartScreen「未知发布者」警告，用户需点「仍要运行」；企业 IT 可能直接拒绝。这是已知且已接受的取舍。

### 3.2 签名与密钥保管

| 项 | 方案 |
|---|---|
| 签名对象 | `SHA256SUMS`（所有发布文件的行式哈希清单） |
| 签名算法 | minisign（Ed25519）优先；GPG 兼容 |
| 私钥位置 | **构建机本地**（不服务器、不仓库、不 CI 云端） |
| 私钥保护 | 口令保护；不写入任何记录文件；不进 Git |
| 公钥分发 | 随包放 `安装信息.json` 旁；同时在发布页公布指纹 |
| 泄露处置 | 立即吊销 + 重新签发 + 公告 |

**硬约束**：私钥**永不**进入仓库、日志、任务 JSON；提交前由 `round_evidence.SECRET_PATTERNS` 与 `test_secret_sink_audit` 扫描。

### 3.3 更新包完整性校验链

```
发布：构建 → distribution_build.py 生成 分发清单.json（逐文件 sha256）
     → 生成 SHA256SUMS → minisign 签名 → 发布（包 + 清单 + 签名 + 公钥）

安装/更新：下载包 → 读内嵌 分发清单.json → 逐文件比对 sha256（verify）
         → 用公钥验 SHA256SUMS.sig → 指纹比对 → 通过才安装
```

**设计要求**：
1. 更新流程**必须**调用 `distribution_build.verify()`，不能只比版本号（当前 `update_notice.py` 的缺陷）。
2. 签名验证**只放发布与自检通道**，不进启动路径（规则 33 启动零递归扫描）。
3. 校验失败必须**拒绝安装**并明确提示，不得「警告后继续」。

### 3.4 何时升级到 Authenticode

满足任一条件时重新评估：

1. 第一个企业客户明确要求签名的安装包。
2. 付费用户超过 100，SmartScreen 警告成为可测量的转化损失。
3. 上架 Microsoft Store 或其他需要签名的渠道。

## 4. SBOM（物料清单）

| 项 | 方案 |
|---|---|
| 格式 | **CycloneDX 1.5 JSON** + 人读 `sbom.txt` |
| 生成器 | `scripts/sbom.py`（stdlib-only），`distribution_build.py` 默认调用 |
| 内容 | 主程序精确生产依赖、离线 ASR 完整传递锁（optional）、随附解释器与 FFmpeg 锁、外部技能包来源与固定树哈希 |
| 粒度 | **组件级**；逐文件完整性由同包 `分发清单.json` 承担，避免重复巨型清单 |
| 数据复用 | `external_tools.lock.json`、`voice_engine/supply_chain.lock.json`、外部技能包固定提交与树哈希 |
| 校验 | `distribution_selfcheck --release` 校验 SBOM，组件出现 `NOASSERTION` 或供应链锁不一致即阻断发布 |

## 5. 企业部署通道

| 通道 | 支持方式 |
|---|---|
| 组策略（GPO） | MSI 可通过 Software Installation 策略分发 |
| SCCM／Intune | MSI + `/qn` 静默参数 |
| 命令行静默 | MSI：`msiexec /i 包.msi /qn`；EXE：`/VERYSILENT` |
| 许可证 | 每机或每用户由 MSI 属性控制；兑换码批量生成（服务端 `scripts/gen_redeem.py`） |
| 离线部署 | 安装包自包含（含解释器与 FFmpeg），无需联网 |

**教育机构场景**（PRD §1.2 画像 P4）：机构采购会员 + 批量兑换码 + MSI 静默部署，学员机无需 API Key（用机构统一配置）。
