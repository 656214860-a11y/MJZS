# ADR-0013 UI 框架锁定 Tkinter

- 状态：已接受（2026-11-19，R3785）
- 决策者：用户 + 执行 agent
- 相关：ADR-0002（依赖白名单）、ADR-0005（隐藏桌面测试）、`说明/技术选型对比表` 已并入 `docs/specs/01_架构与技术选型.md`

## 背景

2026-11-19 的设计规格整理中，用户提出「能否更换 UI 框架解决 3000 镜规模的性能问题」。此议题在历史上被反复提及，但从未形成正式裁决，导致每隔数月重新讨论一次。本 ADR 把已有实测证据与裁决固定下来。

## 已实测的性能基线（R3415，只读诊断轮）

参考硬件 i9-12900K／31.70 GiB／Windows 11 build 26100：

| 项目 | 实测值 | 含义 |
|---|---|---|
| 3000 镜 JSON 大小 | 2.52 MB | 数据量本身不是瓶颈 |
| JSON 序列化／解析 | 8.6 ms／9.6 ms | 不是瓶颈 |
| 单镜线性查找 | 0.066 ms／次 | 不是瓶颈 |
| `ttk.Treeview` 插入 3000 行 | 17.8 ms | 不是瓶颈 |
| 目录扫描 21000 文件（`rglob`） | 583 ms | **是瓶颈** |
| 目录扫描 21000 文件（`os.walk`） | 149 ms | 优化路径 |
| **控件数量**（合成 1000 控件） | **明显变慢；滚动中位数 150 ms；内存增量 30 MiB** | **是瓶颈，且换框架也需分页** |

R3415 §H 结论原文：「当前不安装 PySide/Pyzed，不宣布替换框架即可解决事务、重试或容量问题。」

## 已评估并排除的替代方案

| 方案 | 评估依据 | 排除理由 |
|---|---|---|
| PySide6 / PyQt6 | 本 ADR | 需重写 `ui/` 106 个模块 + 上千条 UI 测试；依赖白名单从 6 个扩到约 11 个、体积 +约 200 MB；`design_tokens.md` 与 `ui_components.md` 两份权威文档作废；单人开发工期 3–6 个月，期间无法交付 |
| Electron / Tauri | `维护记录/体积分析_20260921.md` #13、`20260919_自主优化总结.md` | 「本应用不是 Electron，没有 Chromium 可去；迁移等于重写，收益为负」；破坏「随附解释器零装环境」 |
| sv-ttk / ttkbootstrap / CustomTkinter | `tasks_round/UI统一组件标准任务书.md` D2（均已评估，均 MIT） | 会多出第二个样式权威源；项目已有圆角 PNG、悬停渐变、`ui_tokens`、Fluent 图标 |
| 混合 WebView（分镜表／资产库嵌 Web） | 本 ADR | 引入 WebView2 依赖、两套 UI 技术维护成本、`ui_tokens` 与 CSS 变量需手工同步 |

## 决定

1. **UI 框架锁定 Tkinter**，不更换框架、不引入第二套 UI 技术。
2. 3000 镜规模问题按以下方式解决，**均不涉及换框架**：
   - 目录扫描：写入路径先查 `infra/artifact_index`，不盲扫（详见 `docs/specs/04_数据与本地存储.md`）。
   - 表格：分页（每页 ≤100 行）+ 筛选；表格内不放缩略图（`asset_thumbs` 是实测热点）。
   - 长任务：`Desktop.async_()` 全生命周期经 `BackgroundTaskLifecycle`，不在 UI 线程同步扫描。
3. 后续若再提更换 UI，**必须先推翻本 ADR**，并以真实测量证明：Tkinter 在分页 + 索引方案下无法达到验收目标。不得以「感觉卡」为由重启迁移。

## 后果

- **正面**：产品可持续交付；不新增依赖；两份 UI 权威文档继续有效；测试体系不作废。
- **负面（如实记录）**：3000 镜无法做到 Excel 式无级滚动与即时排序；分页切换有感知延迟；复杂数据网格的交互体验低于专业框架。此为已接受的取舍。
- **边界**：本 ADR 只锁定「框架」，不锁定具体控件实现。若未来出现 Tkinter 生态的成熟虚拟表格库且满足白名单约束，可按正常选型流程引入。

## 复核条件

满足任一条件时重新评估：
1. 实测证明分页 + 索引下，3000 镜的分镜表操作 p95 超过 500 ms。
2. 出现 Tkinter 生态内、满足「白名单 + 零装环境」约束的成熟虚拟表格库。
3. 团队规模从 1 人扩到 3 人以上，且有专职前端。
