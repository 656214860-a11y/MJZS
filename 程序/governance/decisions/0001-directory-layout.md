# 目录结构与文档唯一入口

- 状态：已接受，2026-11-19；本次目录治理任务范围内执行。
- 责任角色：项目维护者。机器协议：`../structure.json`。本决策是目录规则的唯一理由记录，docs/adr只建指向索引，不复制正文。

## 背景与问题

工程文档分散在程序根、docs、说明，账户完整设计与七册设计重复且状态不一致。生产资源示例和开发文档混放，整目录分发会把治理资料带入产品；反向排除又会丢掉练习项目。主树存在多个会话并发，结构治理必须避免批量重置、重复权威与大爆炸源码重排。

## 考虑过的选项

1. 全仓改src英文目录并按业务包重排：会牵动启动器、导入、打包、测试ROOT和用户部署，不在本轮范围。
2. 保留docs与说明双入口：同一主题难发现、引用漂移，不采纳。
3. 保持程序源码根，统一文档docs，机器协议加身份棘轮：采用。
4. 仅检查违规总数：可通过等量替换绕过，不采纳。
5. 把所有旧文件放legacy：混淆缓存/证据/仍在用兼容代码，不采纳。

## 决定

- 程序承担src角色；现有contract/infra/domain/orchestrator/ui分层包保留。层级是依赖规则，不声称源码已按业务模块改造。
- tests保留位置，同名测试推导被测对象，跨模块契约测试显式归属。目录是否嵌套与关键词筛选能力分开，不以未经核实的“不支持子目录”作为理由。
- docs唯一工程文档入口，requirements/specs/process/guides/contracts/records按用途归档；根标准入口与现行权威用链接纳入导航，不复制正文。
- 中文文档允许；新目录英文小写，代码小写下划线；不再新建日期/版本副本，历史任务与标准工具名分类豁免。
- 深度上限4指自有源文件父目录相对程序的组件数；根模块深度0是接受现状。不约束用户工程、vendor内部、gitlink内部与历史凭据。
- 第三方、运行、私有、构建目录有明确归属/排除；不跟随链接或工作树。不因“为了整齐”批量改运行资源路径。
- legacy只有实际确认退役对象才创建。它不收.bak或升级备份，不承担回滚；回滚由Git负责。仍在执行的legacy_migration等模块不会因为名字而被移入legacy。
- 签名/安装/SBOM未来配置由packaging承担；当前无配置就不造空目录，私钥不进仓库。
- 结构门禁先冻结迁移前违规集合，再迁移；只接受明确的旧命名/深度/测试归属债务，硬边界不得豁免。

## 后果

文档能按任务查找，账户规格只有一份完整权威，示例资源与开发文档分发职责分离。存量命名不会一次清零，必须通过身份棘轮阻止新增，并在触及模块时逐步消减；规则与测试也需要共同维护。

## 复核条件

出现新运行时/服务边界、团队分工或独立发版组件时复核角色与owner；业务包重排另立有消费者与迁移证据的任务，不由本协议自动触发。发现规则误报时先复现并修规则，不直接刷新基线放过新增违规。
