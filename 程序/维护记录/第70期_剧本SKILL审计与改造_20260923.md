# 第 70 期 剧本 SKILL 审计与改造（2026-09-23）

**任务来源**：桌面上的附件《剧本阶段SKILL审计命令》8 条——任务 1～4 是审计，任务 5～7 是「缺什么
补什么」，任务 8 要五份交付物。用户原话：「1. 完成附件任务;」

**先纠一个前提**：附件说「扫描 7 个 SKILL」，**剧本阶段实际是 5 个**。注册表里 11 个阶段每阶段
恰好 5 个（共 55 个，`test_skills.py` 的 `test_fifty_skills_five_per_stage` 硬盯着这条），这不是
漏扫，是真数。下面按 5 个出表，不硬凑成 7。

**一句话结论**：5 个里 3 个核心、1 个支撑、1 个重叠、**0 个冗余**；五类 JSON 原先程序里一份都没有，
本期把契约与产出补齐（新增 `script_contract.py`）；角色物理特征改成五件字段化；ID 唯一性落成
可调用的检查与重发号。改动全在「插入与约束」这一侧，老文件照旧读得出来。

两条扫描发现：

1. `script-structured-generation` 自相矛盾：frontmatter 的 description 写「转化为结构化 JSON 剧本」，
   正文「输入／输出」写「输出结构化剧本 Markdown」。本期按正文登记（正稿是 Markdown；JSON 那一路由
   三类 manifest 与分镜阶段的 shotChain 承担），并在正文里补了一行「三类清单的字段由它定型」。
2. 所有 SKILL 的 `input`／`output` 都是**符号名**（characterProfiles、emotionCurve…），全项目搜
   这七个符号名**零命中**：下游是照「项目里的文件与字段」消费的，不是照这些键名。所以第二节的
   Q1 按「产物有没有人读」回答，不按 frontmatter 里写了什么回答。

## 四、任务 5：五类 JSON 的补全

- **原来的状态**：全项目搜 `character_manifest|scene_manifest|prop_manifest|scene_breakdown|
  emotion_curve|physical_features` → **零命中**，五类一份都没有。所以任务 5／6／7 是缺，必须真补。
- **补法**：新增 `程序/script_contract.py`——`MANIFESTS` 是那五个文件名，`manifest()` 把条目收成
  「抬头三件（manifest／kind／items）＋ items」，`completeness()` 出完整性报告；`stage_layout.STAGES`
  的 00_script 输出直接接 `script_contract.STAGE_OUTPUTS`（一处定义、两处用，不会各写一份）。
- **产出者与落点**：

| manifest | 产出 SKILL | 这一步属于哪一阶段 | 落点 |
|:---|:---|:---|:---|
| character_manifest.json | script-character-extraction | 剧本准备 | 00_script/output/ |
| scene_manifest.json | script-character-extraction | 剧本准备 | 00_script/output/ |
| prop_manifest.json | script-character-extraction | 剧本准备 | 00_script/output/ |
| emotion_curve.json | script-emotion-curve | 剧本准备 | 00_script/output/ |
| scene_breakdown.json | storyboard-scene-breakdown | **初步分镜** | 00_script/output/（剧本阶段自己核对一遍） |

场次拆分那个 SKILL 归在「初步分镜」，产物按契约落在剧本阶段的 output 里——`PRODUCERS` 里照实写，
报告里别把它算成剧本阶段自己的 SKILL。

## 五、任务 6：物理特征字段化

五个键：`skin_tone`（肤色）／`hair`（发型发色）／`eyes`（眼睛）／`distinctive_marks`（标志性特征）／
`body_type`（体型）。`script_contract.field_features()` 负责收：

- 字符串＝整句自然语言：按中文标点切片段，逐片按关键词归位；**长的关键词优先**（别让「短发」被「发」
  抢走），认不出来的片段留在 `raw` 里，**原文不丢**；
- 对象：补齐缺的五个键，别的键一个都不动；老写法（一整句塞在其中一个键里）也认——拆得出两个以上
  字段就地拆开；
- 空值：给五个空串，不编。

同一件事在资产侧也做了：`asset_contract` 的角色资产补了 `physical_features`（defaults／normalize／
validate／schema 四处），老资产少这个键照旧读得出来；`validate` 里整句自然语言会被点出来。

## 六、任务 7：ID 唯一性

编号口径：角色 `CHAR_###`／场景 `LOC_###`／道具 `PROP_###`／场次拆分 `SC_###`／情绪节拍 `EC_###`。
三件套：

- `duplicate_ids(manifests)`：同一份里重复、跨份撞号、缺编号，都报出来；
- `reassign_ids(manifests)`：先出现的号留着，后面的往空号上排，改动一条一条列出来（形状照旧：原来
  是带抬头的对象改完还是对象，原来是数组改完还是数组）；
- `unique_ids(manifests)`：验收口径（任务 7 的那句「检查所有 manifest 中的 ID 是否唯一」）。

实测一处值得记着：跨类别撞号会连前缀一起换——`CHAR_002` 落到场景清单上会重发成 `LOC_001`。

### 7.1 五类 Schema 的必填与值域

| manifest | 抬头必填 | 条目必填 | 条目可选 | 值域与约束 |
|:---|:---|:---|:---|:---|
| character_manifest.json | manifest／kind／items | character_id／name／physical_features | aliases[]／description／image_prompt | character_id 合 `^CHAR_[0-9]{3,}$`；physical_features 五件都是字符串 |
| scene_manifest.json | 同上 | scene_id／name | description／time_of_day／weather／image_prompt | scene_id 合 `^LOC_[0-9]{3,}$` |
| prop_manifest.json | 同上 | prop_id／name | description／holder／image_prompt | prop_id 合 `^PROP_[0-9]{3,}$`；holder 写角色编号或留空 |
| scene_breakdown.json | 同上 | breakdown_id／scene_id／order | episode_id／time_place／characters[]／task／boundary | breakdown_id 合 `^SC_[0-9]{3,}$`；characters 只能写 CHAR_###；order ≥ 1 |
| emotion_curve.json | 同上 | beat_id／scene_id／intensity | episode_id／order／reason／hook／turn | beat_id 合 `^EC_[0-9]{3,}$`；intensity 取 1～10 的整数 |
