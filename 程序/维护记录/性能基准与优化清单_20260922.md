## 2. 性能基准（本机实测，2026-09-22）

量测口径：

- 冷启动＝外部墙钟「起进程 → 主界面首帧画出来」，含解释器启动。与 `启动助手.cmd` 的差别：没有 `-I`、没有单实例互斥，并且把启动时那个「选择项目」弹窗换成了空函数（否则基准会被模态框挂住，量到的不是启动时间）。
- 本机此刻还有两个正在运行的助手实例（PID 24256／30412），基准是在另外的进程里跑的，没有打扰用户正在用的窗口。
- 运行间波动不小：同一天里全量自检跑了三次，148.9 s／184.6 s／247.3 s（最大差 66%，受机器负载影响）。读数按数量级看，做门槛要取中位数。

**第 72 期补上了 30 分钟长跑**（`维护记录\基准脚本\基准_内存长跑.py`：300 项资产的清单，每轮把
11 页来回开一遍＋资产页开一次，每分钟记一笔；实测 30.1 分钟 / 221 轮）：

| 指标 | 实测 |
| --- | --- |
| 工作集 | 69.5 → 107.4 MB（峰值 107.4 MB，第 26.6 分钟） |
| 热身 → 中段 → 收尾 | 82.3 → 105.1 → 107.3 MB（中段到收尾 Δ+2.2 MB） |
| 后半程斜率 | +0.140 MB/分钟（约 +8.4 MB/小时） |
| 控件数 / Tk 图元数 | 95 → 95 / 13 → 13（两条都不动） |

结论：**没有「对象堆积」型泄漏**——界面侧硬指标 30 分钟一动不动，前 5 分钟那 +28 MB 是预热
（页控件、图元、字体度量缓存一次性长到位）。但工作集这 30 分钟**没有走平**，后半程仍以
约 0.14 MB/分钟上漂（换算 8 小时约 +67 MB）。再补一把归因（5 分钟，开着 tracemalloc 所以那次
MB 数字不作数）：Python 对象 26688 → 26772（+84 条，其中一半是探针自己的快照结构）、Tk 图元
8 → 8，Python 侧能解释的存活增长合计约 1.6 MB（最大两处是 `responsive_ui.measure` 的字体宽度
记忆缓存，上限 20000 条；以及每次建页重读的项目 JSON）。也就是说漂移主要在 C 层（Tk／GDI／堆），
不在应用层对象上；要定性得上 Windows 堆快照（umdh／VMMap），不在本轮范围。

## 4. 优化清单（按附件「五.3」的 P0／P1／P2／P3 排序）

每条都按「现状数据 → 目标 → 做法 → 量测 → 风险／回滚」写，便于逐项执行、逐项回滚。

### P0-1　资产管理页打开慢（300 行 0.93 s／999 行 0.63～0.85 s，目标 < 0.3 s）

- 目标：300 行 < 300 ms；999 行 < 600 ms。
- 做法：① 先建文字行，缩略图交给 `after_idle` 后续贴（打开即见表格）；② 行数超过阈值（默认 200）时只渲染可见窗口——Tk 没有虚拟列表，用 `Treeview` 的 `height` + `yview()` 回调换算窗口是最省事的一条；③ 把「行数 × 0.85 ms」的同步循环拆成每帧 50 行。
- 量测：`维护记录\基准脚本\基准_长列表.py` 的 cold_ms／warm_ms。
- 风险：中（行与勾选状态、`cell_images` 的坐标换算纠缠在一起）。回滚：三处改动彼此独立，加一个开关常量就能退回原路。

### P0-2　内容框滚动掉帧（300 行 28 ms/帧、999 行 56 ms/帧，目标 16.7 ms/帧）

- 做法：① 滚动期间不重建、不重算缩略图（只贴已缓存的图元）；② 悬停高亮在滚动中只做一次 `clear`（已经这么做），把「重新算悬停格」延后到滚动停止 120 ms 之后；③ 缩略图长边维持 72 像素，不再放大。
- 量测：基准脚本的 scroll_avg_ms／scroll_max_ms。
- 风险：中（悬停高亮与滚动的坐标换算，第 58 期第 2 条刚动过）。回滚：单文件改动。

### P0-3　缩略图冷加载 45.7 ms/张、且没有磁盘缓存

- 目标：同一张图第二次开软件 < 3 ms。
- 做法：① `asset_thumbs.thumbnail` 落一份磁盘缓存（`<项目>\episode\.thumbs\<路径哈希>_<长边>.png`，命中就直接 `PhotoImage(file=...)`）；② 只给可见行生成；③ 保持「一张图一个图元、图元常驻」不变（第 30 期踩过的坑）。
- 量测：同一张图冷／热两次开软件的时间。
- 风险：低（新增缓存目录，随时可删）。回滚：删目录 + 一个常量开关。

### P1-1　性能回归门禁

- 现状：2093 条功能自检、0 红，但没有任何耗时断言。
- 做法：新增 `test_perf_baseline.py`，把本报告 6 张表的数字写成**宽松阈值**（乘以 1.5 或取中位数 ±3σ）：启动首帧 < 1500 ms、单页打开 < 800 ms、300 行滚动 < 45 ms/帧、缩略图平均 < 70 ms/张、内存增量 < 30 MB。
- 风险：低（阈值宽松，只拦「明显退化」）。回滚：删文件。
- 落地情况（第 72 期）：`test_perf_baseline.py` 5 条已写好并接进门禁。另外发现两处必须一起改，
  否则门禁自己会误报：① 性能用例不能和别的 Tk 用例挤并行池——同一个动作单独跑 0.4 s、挤在
  并行池里 3.9～6.8 s（Tk 建控件与字体量宽是全机共享的资源），`run_selftests.py` 现在把
  `test_perf_*.py` 挑出来排在并行池之后串行跑；② 这台机器 CPU 有效频率会掉到额定的 42%
  （整机慢 2.4 倍），写死的毫秒阈值必然误报，资产页打开改判「CPU 时间 ÷ 同一次运行里现量的
  参考活」的比值（上限 10 倍，满速时约 4.4、降频时 3.9～6.5）。
