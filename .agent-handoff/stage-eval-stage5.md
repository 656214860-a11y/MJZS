## A 结论与前提交代

本产品是**单机单用户 Windows 桌面应用**（无服务器、无账户、无多租户流量）。用户给的五条角度里，**「灰度发布（小流量看错误率）」「GPU 利用率」「用户留存」在本项目没有原始形态**，硬凑就是伪造攻击面或指标（与阶段4 T12 同一处理）。可映射的真实对照面：

| 用户口径 | 本项目对应物 | 现状 |
| --- | --- | --- |
| CI/CD 一键构建·测试·部署 | `本地CI.cmd`→`scripts/local_ci.py`（四模式）＋`scripts/dev.py`（九子命令）＋`scripts/distribution_build.py`/`distribution_selfcheck.py` | 有工具，**无流水线载体**，构建校验不在出口内 |
| 灰度发布 | 只有整机覆盖式升级（用户 2026-09-17 授权解压覆盖 `D:/漫剧制作助手`） | **无灰度通道、无发布后观察判据** |
| 回滚（模型/Prompt/数据迁移） | 源码靠 Git；安装物靠 `distribution_build.py` 从 Git 重建；数据迁移按「只加键、不改写」设计 | 有机制，**无发布标签、无版本↔提交映射、无演练凭据** |
| 监控告警 | `app_logging`（轮转＋脱敏＋崩溃钩子）、`task_center_service`/`task_center_ui`「运行状况」、`diagnostic_capture` 脱敏诊断包、`缺陷台账` | 有留痕，**无指标聚合、无比率、无阈值告警** |

## C 优化清单 U1–U13（待确认，不自动执行）

### CI/CD 自动化

- **U1（无流水线载体）** 现状：`本地CI.cmd exit` 已是机器可判定出口，但**没有任何自动触发点**——仓库无 `.github/workflows`、`.gitlab-ci.yml`、`azure-pipelines.yml`（本机实测三者均不存在）；`pre-commit` 只做全量锁与 allowlist 检查、不跑测试；`ci_*.cmd` 全靠人手点。建议：给 `exit` 加一个提交后自动触发（post-commit 或计划任务），并把 `logs/ci_最近.log` 摘要落成可核查凭据。代价：每次提交约 4 分钟机器时间；须先解决它与后台全量补跑的互斥。
- **U2（构建校验不在出口内）** 现状：`distribution_selfcheck`（能否真正复制成正式副本、副本缺不缺文件与标准库）只在 `dev.py dist` 与测试套件里跑，`exit`／默认 CI 都不含；而它历史上曾两次红（R1462–R1466）。建议：发布前必跑，把「`--verify` 通过」写进发布检查单；成本可接受就把 `dist` 挂进 `exit`。代价：构建＋校验＋导入约数十秒。
- **U3（发布物与提交未绑定）** 现状：`分发清单.json` 有 `version` 与逐文件 `sha256`，但**没有提交哈希或轮次**；`VERSION` 从 R1460 起一直是 `V0.7`，`更新记录.md` 只有一个 `V0.7` 小节 → 拿到一份分发副本无法判定它对应哪个提交。建议：`build` 报告写 `git rev-parse HEAD`＋轮次；`更新记录.md` 每版加「起始提交／结束提交」。代价：极小。

### 灰度发布

- **U4（无灰度通道）** 现状：升级＝整机覆盖（`维护约定.md` 第 1、5 行：交付后自动解压覆盖 `D:/漫剧制作助手`，保留原配置、API 密钥、项目、素材与任务记录），只有一份安装目录，没有并行版本、没有分批、没有回退窗口。建议：至少定义「升级前快照」（覆盖前把 `程序/` 中被替换的文件与 `app_metadata.VERSION` 记一份），使覆盖式升级**可退**；多版本并存不建议做（单机成本高于收益）。代价：一份程序目录副本（多为可再生内容，实际增量小）。
- **U5（发布前后无检查单）** 现状：`runbook.md` §3／§5／§6 有自检、升级、故障三段，但**没有一张可勾选的发布检查单**（构建→副本自检→更新记录→VERSION→快照上一版→安装→启动冒烟→观察窗口→回滚触发条件）；阶段4 §7 只有测试侧检查单。建议：新增 `说明/发布检查单.md`，每项标注命令与期望输出。代价：纯文档。
- **U6（无发布后观察判据）** 现状：灰度出口「无严重问题／SLO 达标」没有可执行定义；本机可得观察源是「运行状况」面板（近期任务历史、失败原因、可重试、被忽略异常）＋逐笔费用台账＋`缺陷台账`，但没有「观察多久、看哪几个数、超过多少算回滚」的规则。建议：定义时间盒与判据（如：升级后首个 10 镜项目完成、失败率 0、无新增 A 级缺陷、单分钟成本不超 X），X 与样本数由用户定。代价：纯文档。**注意**：8 项实际使用验收（含 P1-1 真实成本、P1-2 预算、P2-1 首次体验）已按用户要求延期，本项只登记判据，不代替那批验收。

### 回滚方案

- **U7（无发布标签、无版本↔提交映射）** 现状：`git tag` 只有 5 个 `rescue/*`（2026-10-04），**没有发布标签**；`安装信息.json` 的 `0.6-20260918` 是安装残留且无代码读取（R1460 已记录）。建议：每次交付打 `release/V0.7-<日期>-R<轮次>` 标签，或至少在 `更新记录.md` 记提交哈希。代价：极小（`.git` 被 `distribution_manifest.md` 排除，不影响分发）。
- **U8（回滚从未演练、无凭据）** 现状：`runbook.md` §5 写明回滚靠 Git，但**没有任何一次回滚演练记录**，出口标准「回滚验证通过」无证据。建议：在隔离目录演练一次（从上一发布提交 `distribution_build.py --build` → `--verify` → 副本自带解释器跑默认冒烟），产出报告；不碰当前安装目录与用户数据。代价：约 5–10 分钟。
- **U9（文档冲突：安装器不存在）** 现状：`说明/维护约定.md:9` 要求「使用 `maintenance_latest/install_release.py` 安全安装」，但该文件与目录全盘不存在（`维护记录/体积分析_20260921.md:491` 已记录「D:\ 全盘没搜到」）；实际升级＝手工解压覆盖。建议：把 `维护约定.md` 改成与 `runbook.md` §5 一致的口径（谁在什么条件下覆盖、保留哪些目录、如何核对落位），不再引用不存在的脚本。代价：纯文档。
- **U10（配置回写无写前备份）** 现状：`scripts/migrate_workflow_presets.py --apply` 会回写项目 `skill_config.json`（`:116 apply()`），默认干跑、确认后才写，但**写前不落快照**；模型池切换也只有「每笔任务记录配置版本」（`程序/model_pool.py:59`）可溯源，无配置快照。建议：写前把原文件另存到 `维护记录/配置快照_<日期>/`，失败可原样放回。代价：小。
- **U11（版本漂移检测不全）** 现状：`持久化产物版本清单.md` 仍列「待核查」项：`assets.json`、`skill_config.json`、`natural_script_selection.json`、批次/三元组台账、`产物来源关系.json`、各 manifest 未确认有无版本字段 → 「格式漂移能被检出」覆盖不全。阶段4 清单未含此项（T4 只做提示词结构不变量）。建议：按「读源码→确认版本→登记或补 `schema_version`」逐项收口。代价：中等。
- **N/A（数据库迁移回滚）**：随附解释器 `sqlite3` 缺失（本机实测），产品无数据库。**数据库迁移回滚不存在**，显式记 N/A，不凑数。

### 监控告警

- **U12（无指标聚合与阈值告警）** 现状：留痕齐全但**没有聚合**——产品代码 0 处命中「失败率」「遥测」（「埋点」只命中 SKILL 文案「长线埋点」，非产品埋点）；「运行状况」只列近期事实、不算比率；成本只有逐笔台账，**无累计超限预警**（「预算」字样只在 SKILL 文本里）；失败处理有分类与手动重试，但**无「连续失败 N 次→提示／暂停／降级」的阈值规则**。建议：在既有面板加三条只读比率（近 N 次任务失败率、编码失败率、累计金额对比预算），并给「连续失败」定提示阈值。注意：这是本地单用户面板，不是告警系统；不做远端上报（与隐私口径一致）。代价：中等（服务层统计＋面板一行）。
- **U13（N/A 显式登记）**：**GPU 利用率**——生成走供应商 API 与外部 Blender/ffmpeg，本机无自建 GPU 训练或推理队列，记 N/A（不显式登记容易被读成漏做）；**用户留存**——单机单用户、无账户、无远端统计，记 N/A；**多租户 SLO**——同前。适用的监控面是 U12 的三条本地比率＋「运行状况」＋脱敏诊断包。
